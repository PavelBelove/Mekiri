# Дизайн: sprout/harvest для mekiri-host

**Проект:** Mekiri
**Статус:** спек, ожидает ревью пользователя
**Контекст:** [whitepaper.md](../../../whitepaper.md), [tz.md](../../../tz.md), [2026-07-24-core-primitive-design.md](2026-07-24-core-primitive-design.md) (полная целевая архитектура), [2026-07-24-mekiri-host-minimal-design.md](2026-07-24-mekiri-host-minimal-design.md) (prune-итерация, уже реализована и одобрена), `packages/mekiri-core` (`createBranch` уже поддерживает `branchType:"sprout"`, но пока никем не вызывается)
**Скоуп:** вторая половина примитива — тёплый клон (`sprout`) и его завершение (`harvest`), в том же минимализме, что и prune-итерация: только `wait_mode: "sync"`, `depth_limit` жёстко читается из конфига (без `configure_mekiri` — этой тулзы в этой итерации нет), без `parallelism > 1`.

**Вне скоупа этой итерации:** `promote` (замена лидера форком — см. `Mekiri.md`, зафиксировано как видение на будущее, не проектируется здесь), ACP-адаптер, `configure_mekiri`, `async` wait_mode, `interrogate`-режим.

---

## 1. Ключевое упрощение: sync-режим не требует конкурентных луп

Поскольку `wait_mode` в этой итерации всегда `"sync"`, тулза `sprout` — это просто `async`-хендлер MCP-тулзы: он сам, изнутри своего `await`, прогоняет дочернюю сессию клона до конца и возвращает harvest как обычный tool_result. Родительский `for await`-цикл в `repl.ts` (уже реализован, уже одобрен) не меняется вообще — с точки зрения SDK родитель просто ждёт ответа на вызов тула, как на любой другой.

---

## 2. Модель исполнения клона

Новая функция `runClone(task, depth, context)` в `packages/mekiri-host/src/clone.ts` — свой `for await`-цикл поверх `query()`, структурно похожий на `repl.ts`'s внутренний цикл (переиспользует `createInputQueue`, `createLiveTranscript`, `createMekiriTools`), но:
- **Без readline.** Входной поток — `createInputQueue()`, куда проталкивается ровно одно сообщение (`task`) и сразу вызывается `close()`. Клон работает автономно: тулзы (включая `prune`) он вызывает сколько угодно раз в рамках одного захода, без нового ввода снаружи.
- **`prune` внутри клона работает полноценно**, тем же паттерном `pendingSwitch` → `q.return()` → новый `query({resume, forkSession:true, prompt})`, что и у родителя — просто без readline и с собственным `liveTranscript`, обнуляемым при каждом внутреннем переключении. Это осознанно важное свойство, не побочный эффект: провал гипотезы внутри клона должен откатываться (в т.ч. `keep_code:false`, мутационный дебаггинг) так же, как у родителя — иначе клон копит артефакты неудачных попыток вместо чистого финального пути.
- **Отдельная функция, не общая абстракция с `repl.ts`.** Дублирование каркаса цикла (`for await` + обработка `pendingSwitch`) принимается сознательно — риск сломать уже одобренный и живущий в проде parent-REPL общей рефакторингом перевешивает выгоду от переиспользования на этом этапе.

### Завершение клона

- **Штатно** — вызов `harvest(result)`: хендлер ловит это как терминальный сигнал (аналог `pendingSwitch`, но без нового `query()` — просто останавливаем `for await` через `q.return()` и возвращаемся).
- **Мягкий фолбэк** — клон закончил ход (`stop_reason` без вызова тула), не вызвав `harvest`: не ошибка, а автоматическое обёртывание последнего текста ассистента как результата, с пометкой в отчёте родителю (`harvested_implicitly: true` в служебных метаданных tool_result), что явного вызова `harvest` не было.

## 3. Схемы тулз

Обе тулзы — **постоянно зарегистрированы во всех сессиях** (родитель, клон, откаченная ветка), по инварианту кеша из `2026-07-24-core-primitive-design.md` §2: список тулз должен быть byte-identical везде, иначе кеш ломается на каждой ветке. `harvest`, вызванный вне контекста клона, — не отсутствующая тулза, а рантайм-ошибка.

```ts
sprout({
  task: string,             // новая главная задача клона, дописывается в конец копии контекста
})
→ { status: "ok", branch_type: "sprout", child_session_id: string, result: string, harvested_implicitly?: true }
  | { status: "depth_limit_exceeded" }

harvest({
  result: string,
  needs_clean_look?: boolean,   // самоэскалация вместо честного результата (tz.md §6.3)
})
→ { status: "ok" }
  | { status: "error", reason: "harvest валиден только внутри sprout-клона" }
```

`depth_limit` не передаётся аргументом тулзы (в отличие от полного дизайна из `2026-07-24-core-primitive-design.md`) — читается из `.mekiri/config.json` через уже существующий `mekiri-core`'s `loadConfig`/`defaultConfig` (дефолт 1), поскольку `configure_mekiri`-тулзы в этой итерации нет и настраивать нечем. Текущая глубина отслеживается через `context.depth` (0 у родителя, +1 на каждый вложенный `sprout`), сравнивается с `depth_limit` до форка — при превышении форк не создаётся, `createBranch`/`forkSession` не вызываются вообще.

## 4. Fork и audit-log — разнесены по времени

`mekiri-core`'s `createBranch` объединяет `forkSession` и `appendAuditEntry` в один атомарный вызов, что подходит для `prune` (длины известны заранее), но не для `sprout` (длины клона и харвеста известны только по факту завершения). Поэтому `sprout`-хендлер **не использует `createBranch`** целиком:

1. В момент вызова `sprout` — прямой вызов SDK'шного `forkSession(sessionId, {dir})` (тот же примитив, что использует `mekiri-core` внутри `createBranch`, но без слайса — полная копия) → новый `child_session_id`, тёплый кеш, родитель не тронут.
2. `runClone` прогоняется до завершения (harvest или фолбэк).
3. После завершения — `mekiri-core`'s уже экспортированный `appendAuditEntry` (без `createBranch`) с реальными `branchLength` (символьная длина накопленного `liveTranscript` клона) и `harvestLength` (символьная длина результата).

`mekiri-core` не меняется — оба использованных примитива (`forkSession` из SDK, `appendAuditEntry` из `mekiri-core`) уже экспортированы.

---

## 5. Тестирование

Тот же минимализм, что в prune-итерации: 1-2 дешёвых живых smoke-теста на сам механизм (клон форкается тёплым, реально работает, харвестит явно или через фолбэк, родитель получает результат синхронно) — плюс ручное догфудирование, специально включающее сценарий «гипотеза А не сработала → откат внутри клона → Б → В → Г получилось», описанный пользователем как ключевой мотивирующий кейс для этой фичи.
