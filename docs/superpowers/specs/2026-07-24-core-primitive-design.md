# Дизайн: ядро примитива rollback/fork_warm (Фаза 1)

**Проект:** BonsAI — метафора: компактизация как стрижка до пеньков, fork_warm как росток из семечка, rollback как мелкая корректирующая обрезка. Контролируемый рост дерева сессий мелкими правками, а не годами нестриженной листвы.
**Статус:** спек, ожидает ревью пользователя
**Контекст:** [whitepaper.md](../../../whitepaper.md), [tz.md](../../../tz.md)
**Скоуп:** оба сценария применения единого примитива `spawn(transcript_slice, injected_message, kill_source, timing)` — откат (`rollback`) и тёплый клон (`fork_warm`) — как одна первая итерация, с упором на минимальные различия между ними.

**Примечание об именовании.** Рабочая директория репозитория (`/home/pol/dev/rollback`) не переименовывается в рамках этой итерации — переезд папки на живую сессию рискует спутать привязку к `~/.claude/projects/<hash>`. Бренд/GitHub-репозиторий — BonsAI, пакеты и внутренние пути внутри репо ниже названы соответственно. Имена самих MCP-тулз (`rollback`, `fork_warm`, `report`, `configure_rollback`) оставлены как в tz.md/whitepaper.md — это понятийные термины из уже написанной спецификации, а не элементы бренда.

## 1. Архитектура

Собственный host-процесс на Node.js/TypeScript, построенный на `@anthropic-ai/claude-agent-sdk`, а не обёртка вокруг `claude` CLI или VS Code-расширения.

```
┌───────────────────────────────────────────────────────────────┐
│  bonsai-host (наш процесс)                                   │
│                                                                  │
│  ┌──────────────┐    ┌─────────────────────────────────────┐  │
│  │ ACP-адаптер   │◄──►│ core loop: держит активный query()   │  │
│  │ (форк         │    │ из @anthropic-ai/claude-agent-sdk    │  │
│  │ claude-agent- │    │                                       │  │
│  │ acp)          │    │ rollback → quote→uuid → forkSession   │  │
│  └──────┬────────┘    │   ({upToMessageId}) → переключение    │  │
│         │ ACP JSON-RPC │   consuming-луп на новый query()      │  │
│         │ (stdio)      │                                       │  │
│         ▼              │ fork_warm → forkSession({}) →         │  │
│  Любой ACP-клиент       │   параллельный query() в том же       │  │
│  (Zed / generic VS Code │   процессе → ждёт report() →         │  │
│  ACP ext / JetBrains)   │   возвращает tool_result родителю     │  │
│                         └─────────────────────────────────────┘  │
│                    rollback/fork_warm/report/configure_rollback  │
│                    — in-process MCP-тулзы (createSdkMcpServer)   │
└───────────────────────────────────────────────────────────────┘
```

**Почему не обёртка вокруг существующего клиента.** Официальное VS Code-расширение Claude Code — закрытый компонент; патчить его или перехватывать его процесс-менеджмент — хрупкий путь, ломающийся на каждом обновлении. PTY-супервизор вокруг голого `claude` CLI решал бы это только для терминального сценария и не работал бы под IDE-обёрткой вовсе.

**Почему не ждать ACP-стандартизации.** На момент разработки (проверено напрямую по исходникам, не по пересказу) `session/fork` в ACP — RFD в статусе draft, без параметра `messageId` (только полный форк сессии, без среза по точке); `session/resume`+`replayFrom` — тоже без произвольной точки отката, только полный replay с начала. Прокси-паттерн (`proxy-chains` RFD) — тоже draft, референсная реализация — Rust-прототип на движущемся фундаменте. То есть ACP сегодня не даёт сам примитив среза-по-точке — только будущую возможность его выразить единообразно для разных клиентов.

**Ключевая находка, определившая архитектуру.** В `@anthropic-ai/claude-agent-sdk` (проверено по `.d.ts` реально установленного пакета, версия 0.3.218) уже есть готовая, поддерживаемая функция:

```ts
forkSession(sessionId, { upToMessageId?, title? }) → Promise<{ sessionId: string }>
```
«Copies transcript messages from the source session into a new session file, remapping every message UUID and preserving the parentUuid chain. Supports `upToMessageId` for branching from a specific point in the conversation.»

Это и есть примитив `spawn(transcript_slice, ...)` из мотивационной части — уже реализованный Anthropic, а не наш самодельный байтовый парсер jsonl. Плюс у `query()` есть орто­гональные опции `resume: string`, `forkSession: boolean`, `resumeSessionAt: string` (UUID сообщения ассистента) — то же самое разбиение на параметры, что описано в мотивационной части.

**Роль ACP.** Не транспорт для самого примитива (тот целиком наш, через SDK, в одном Node-процессе), а универсальный протокол для фронтенда: пользователь подключает любой ACP-клиент к нашему хосту вместо закрытого официального расширения. Реализуется форком/расширением открытого `@agentclientprotocol/claude-agent-acp` (уже оборачивает Claude Agent SDK в ACP-агента) — не с нуля.

**Тестирование в Фазе 1.** Ядро (`bonsai-core`: поиск цитаты→uuid, вызов `forkSession`, запись заметки) проверяется на реальных jsonl-транскриптах, которые уже генерирует связка VS Code + официальное Claude Code-расширение (формат файла один и тот же независимо от фронтенда) — до того, как полноценный ACP-хост станет ежедневным драйвером.

## 2. Инвариант кеша (жёсткое правило дизайна)

**System prompt и список тулз обязаны быть byte-identical по всему дереву веток** (родитель / клон / откаченная ветка). Различаться между ветками может только хвост — контент, добавленный уже *после* точки форка.

Причина: кеш у Anthropic префиксный/иерархический — совпадение при каждой `cache_control`-точке проверяется по всему префиксу до неё, а тулзы сериализуются в начало запроса, раньше истории сообщений. Если хотя бы одна тулза присутствует в одной ветке и отсутствует в другой, весь унаследованный (потенциально многотысячный) конversation-history кеш промахивается целиком — экономика тёплого клона (мотивация всего проекта) перестаёт работать.

**Следствия:**
- Набор тулз `[rollback, fork_warm, report, configure_rollback]` — инвариантен и одинаков для родителя, клона и откаченной ветки. `report` **не физически отсутствует** у родителя — она всегда зарегистрирована, но её хендлер в рантайме проверяет роль текущей сессии и возвращает ошибку, если вызвана не внутри клона.
- Фрейминг «ты тёплый клон, вот твоя задача, верни `report` по форме после перепроверки» доставляется **только в хвостовом инжекте** (`prompt` нового `query()` после точки форка), никогда не через изменение системного промпта. Родитель уже понимает из своего собственного (унаследованного клоном) контекста, что такое тёплый клон и зачем — повторного объяснения не требуется, только явное «ты — клон, вот твоя задача» плюс напоминание о `report`.

## 3. Data flow: rollback

1. Агент вызывает `rollback(quote, note_type, note, keep_code)`.
2. Хендлер валидирует обязательные поля `note` по `note_type` **до** любых побочных эффектов (см. §5 схемы).
3. Поиск `quote`: точное вхождение подстроки в текстовых content-блоках `assistant`-сообщений основной цепочки (`isSidechain: false`), в зоне **после** последнего маркера компакта (`compactMetadata` / `isCompactSummary` — точный формат подтверждён на реальных файлах).
   - 1 вхождение → uuid этого `SDKAssistantMessage` — граница.
   - 0 → `not_found`. >1 → `ambiguous`. Цитата внутри compact-зоны → `in_compacted_zone`.
   - Никаких эвристик «взять последнее вхождение» — только точный уникальный матч или явная ошибка.
4. `forkSession(currentSessionId, { upToMessageId: boundaryUuid })` → `{ sessionId: newId }`.
5. Формируется хвостовой инжект: тело заметки (`note`) + служебный блок `[branch_type:rollback, branch:<currentSessionId> archived, parent:main@<boundaryUuid>]`.
6. Текущий consuming-луп над старым `query()`-итератором прерывается (не убийство процесса — тот же Node-процесс, просто перестаём читать старый generator).
7. Стартует новый `query({ resume: newId, forkSession: true, prompt: injectText })`. С этого момента host-луп потребляет новый generator.
8. Старая сессия физически не изменяется и не удаляется — это архив (требование подотчётности, whitepaper §9): полное забывание доступно как рабочий инструмент, но не как акт, стирающий следы.

## 4. Data flow: fork_warm

1. Агент вызывает `fork_warm(task, depth_limit?, wait_mode?)`.
2. `forkSession(currentSessionId, {})` — без `upToMessageId` (полная копия, родитель не грязный, просто ответвляется).
3. Родительский `query()`-луп **не прерывается** — родитель продолжает работать.
4. Параллельно, в том же процессе, стартует `query({ resume: forkedId, forkSession: true, prompt: task })` — с тем же инвариантным набором тулз (§2), включая `report`.
5. Хост детектит вызов `report(result)` внутри дочернего `query()` как сигнал завершения и закрывает дочерний generator.
6. `wait_mode: "sync"` (дефолт) — родительский вызов `fork_warm` блокируется до `report`, возвращает `result` как обычный tool_result. `wait_mode: "async"` — тулза сразу возвращает `{pending: true, child_session_id}`, результат приходит позже отдельным событием в поток родителя.
7. `depth_limit` — счётчик рекурсии клон-в-клоне (защита от бесконечной цепочки форков), **не** про то, как долго клону «жить» как эксперту по домену — это отдельный, вне-скоуповый паттерн (`resume-with-delta`, см. tz.md §10.2, TODO Фазы 2+). При `depth_limit: 0` внутренний вызов `fork_warm` возвращает `depth_limit_exceeded`.
8. Самоэскалация клона (tz.md §6.3) — не отдельный механизм хоста, а обычный вызов `report({needs_clean_look: true, ...})` вместо результата, либо обращение к чистому субагенту — решается на уровне промпта/скилла.

## 5. Схемы тулз

Все тулзы — in-process MCP (`createSdkMcpServer`), Zod-схемы, доступны **везде одинаково** (см. §2).

```ts
rollback({
  quote: string,
  note_type: "portal" | "death_reload",
  note: PortalNote | DeathReloadNote,
  keep_code: boolean = true,
})
→ { status: "ok", new_session_id: string, branch_type: "rollback" }
  | { status: "not_found" }
  | { status: "ambiguous", occurrences: number }
  | { status: "in_compacted_zone", last_compact_uuid: string }

type PortalNote = {
  summary: string,                                     // обязательное
  files_touched?: { path: string, change: string }[],   // обязательное при keep_code:true
  gotchas?: string,
}
type DeathReloadNote = {
  tried: string,
  ruled_out: string,        // обязательное
  facts_learned?: string,
  trigger?: "self_detected" | "user_feedback",
}

fork_warm({
  task: string,
  depth_limit?: number,          // дефолт — из .bonsai/config.json
  wait_mode?: "sync" | "async",  // override конфига на конкретный вызов
})
→ { status: "ok", branch_type: "fork", child_session_id: string, result: string }
  | { status: "ok", branch_type: "fork", child_session_id: string, pending: true }
  | { status: "depth_limit_exceeded" }

report({
  result: string,
  needs_clean_look?: boolean,
})
→ { status: "ok" } | { status: "error", reason: "report валиден только внутри fork_warm-клона" }

configure_rollback({
  patch: Partial<RollbackConfig>,   // глубокий merge, схема валидируется целиком после merge
  reason: string,                   // обязательное — идёт в audit-лог
})
→ { status: "ok", config: RollbackConfig } | { status: "invalid", errors: string[] }
```

**Резервируемая, но не реализуемая в Фазе 1 точка расширения:** `injectionRole: "user" | "assistant"` на уровне `bonsai-core` — роль хвостового инжекта. Дефолт и единственная реализация Фазы 1 — `"user"` (доставляется через `prompt` в `query()`, единственный путь без ручной дозаписи synthetic-энтри в файл сессии). Вариант `"assistant"` — задокументированный TODO-эксперимент («сравнить вес note/task как user-turn vs assistant-turn на внимание модели»), реализация отложена, схема место резервирует.

## 6. Конфиг-слой и самонастройка

**Хранилище:** `.bonsai/config.json` в корне проекта. Читается агентом как обычный файл; пишется только через `configure_rollback` — не запрет на прямое редактирование, а гарантия, что каждое изменение провалидировано схемой и залогировано с `reason` для последующей корреляции с метриками (§7).

**Дефолты Фазы 1** (сознательно консервативные, не «единственно верные»):
```json
{
  "fork_warm": {
    "depth_limit": 1,
    "parallelism": { "mode": "single" },
    "wait_mode": "sync"
  },
  "priorities": { "token_efficiency": "balanced" }
}
```
- `wait_mode: "sync"` — чище, медленнее; осознанный дефолт для первой итерации.
- `parallelism.mode: "single"` сегодня; `{"mode": "parallel", "count": N}` — та же схема, N=1 по умолчанию, N>1 — будущее использование (несколько независимых клонов на декомпозируемую задачу).
- `priorities.token_efficiency: "aggressive" | "balanced" | "irrelevant"` — явная ручка под «токены неважны, лей в контент/качество».

**Скилл `rollback:tuning`** (пишется в Фазе 1, наполняется по мере данных): агент обязан использовать этот протокол при (а) явном заявлении пользователя о приоритете — сразу правит конфиг через `configure_rollback` с `reason: user_override`; (б) накоплении метрик (§7) с явным сигналом — **не меняет конфиг молча**, а формулирует короткий отчёт с количественным обоснованием и спрашивает пользователя «что делаем» — тот же паттерн, по которому велось это самое обсуждение. В Фазе 1 скилл содержит структуру протокола и place-holder пороги; конкретные эвристики — живой документ, наполняется по мере реальных данных.

## 7. Аудит-лог и метрики

Общий append-only jsonl-лог (`.bonsai/audit.jsonl`) фиксирует каждый вызов `rollback`/`fork_warm`/`configure_rollback` с полями, достаточными для постфактум-вычисления формул tz.md §12 без дополнительного логирования сверх того, что уже даёт дерево сессий: длина удалённой/форкнутой ветки, длина заметки/отчёта, позиция относительно истории, факт и момент компакта.

Пре-компактный снапшот (tz.md §8) реализуется той же функцией `forkSession(currentId, {})` по хуку `PreCompact` — полная копия транскрипта до компакта, без побайтового трима. Дёшево, потому что переиспользует уже построенный примитив; `snapshot_id` фиксируется в служебном уведомлении после компакта, как того требует tz.md §8.

Вычисление метрик (Distillation Ratio, Branch Compression, Lifetime Token Savings, Virtual Context Lifetime, Context Recycling Ratio) — отдельная команда, читающая `audit.jsonl` + сессионные файлы постфактум; формулы — tz.md §12.2, без изменений.

## 9. Вне скоупа этой итерации

Явно не входит в эту итерацию (см. tz.md §10 — TODO Фазы 2+):
- `interrogate`-режим (read-only допрос архивной ветки).
- `resume-with-delta` (ветка как постоянный владелец домена).
- `facts_pool` (глобальный пул фактов между несвязанными ветками).
- Explicit merge (кроссовер двух листьев).
- Полноценная реализация ACP `proxy-chains`/`session/fork` как транспорта — сегодня оба RFD в статусе draft; наш примитив целиком реализован через Agent SDK внутри одного процесса, независимо от того, примут ли эти RFD и когда.
