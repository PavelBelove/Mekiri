# Mekiri metrics command — design

**Дата:** 2026-07-27
**Скоуп:** первая рабочая реализация метрик из tz.md §12.2, вычисленных на реальных данных проекта, а не просто формул на синтетике. Явно поставлено владельцем проекта в приоритет над ACP-адаптером и pre-compact snapshot: «сделать рабочие метрики, чтобы доказать эффективность в реальной работе».

---

## 1. Что уже есть, чего не хватает

`packages/mekiri-core/src/metrics.ts` реализует 4 из 5 формул tz.md §12.2 (Distillation Ratio, Branch Compression, Lifetime Token Savings, Context Recycling Ratio) — чистые, unit-тестированы на синтетических `audit.jsonl`-записях. Не хватает:
- Формулы **Virtual Context Lifetime** — нет вообще, ни как функции, ни как алгоритма.
- Вычислительной обвязки, которая кормила бы четыре существующие формулы реальными числами: `lifetimeTokenSavings` и `contextRecyclingRatio` принимают `subsequentRequestCount`/`totalContextProduced` как голые параметры — ничто в проекте их не вычисляет из реальных данных.

Это ровно тот гэп, который `core-primitive-design.md` §7 заранее назвал «отдельной командой, читающей `audit.jsonl` + сессионные файлы постфактум» — до сих пор не построенной.

## 2. Архитектура

Вычисления — в `mekiri-core` (переиспользуемо, тестируемо без живых вызовов SDK), CLI-обвязка — в `mekiri-host` (по тому же разделению пакетов, что и весь остальной проект). Никакого нового пакета не заводим.

## 3. Новые примитивы в `mekiri-core`

### 3.1. `sessionTranscript.ts`

```
readSessionTranscript(dir: string, sessionId: string): Promise<RawLine[]>
```

Читает реальный файл транскрипта сессии — `$CLAUDE_CONFIG_DIR/projects/<sanitizeDir(dir)>/<sessionId>.jsonl`, с фолбэком на `~/.claude` при отсутствии `CLAUDE_CONFIG_DIR`. Парсит построчно в `RawLine[]` — используем существующий тип и конвенцию (`quoteMatcher.ts`/`compactZone.ts` уже работают с `RawLine[]`, а не с SDK-шным `SessionMessage` — сохраняем консистентность, а не заводим вторую модель данных ради этой одной фичи). Отсутствующий файл → `[]`, тот же graceful-degradation паттерн, что у `readAuditLog`.

`sanitizeDir(dir: string): string` — переносится сюда как каноническая реализация из тестового хелпера `packages/mekiri-host/test/helpers/sessionFile.ts` (сейчас там продублирована бы логика, уже сверенная с скомпилированным SDK — см. комментарий в файле). Тестовый хелпer будет импортировать её из `mekiri-core` вместо собственной копии — попутный DRY-фикс, не отдельная задача.

### 3.2. `sessionTree.ts`

```
interface SessionNode {
  sessionId: string;
  parentSessionId: string | undefined; // undefined = корень дерева
  branchType: "prune" | "sprout";
  timestamp: string;                    // из audit-записи
  removedOrBranchLength: number;        // removedBranchLength | branchLength
  fruitOrHarvestLength: number;         // fruitLength | harvestLength
}

buildSessionForest(entries: AuditEntry[]): SessionNode[][]
```

Строит лес деревьев сессий из `audit.jsonl`: каждая prune/sprout-запись — ребро parent→child (`sessionId` → `newSessionId`/`childSessionId`). Группирует записи в независимые деревья по компонентам связности (несколько несвязанных рабочих сессий за время жизни проекта — нормальный случай, не исключение). `configure_mekiri`-записи в граф не входят (у них нет sessionId-рёбер), но участвуют в других уже существующих вычислениях (anti-nag в `mekiri-tuning`) — здесь не нужны. Чистая функция, без I/O.

## 4. Пять метрик

**Distillation Ratio, Branch Compression** — без изменений, уже полностью вычислимы из чисел, лежащих прямо в `audit.jsonl`. Транскрипты не читаются вообще.

**Lifetime Token Savings** — для каждой `prune`-записи: `subsequentRequestCount` = число ходов, случившихся в продолжающейся ветке (`newSessionId`) и её потомках после отката, до текущего момента. Считается обходом `SessionNode[]`-дерева (подсчёт узлов-потомков + опционально числа реальных ходов в транскрипте продолжающейся ветки — контекст: точный подсчёт «ходов» неотличим от подсчёта user/assistant-пар в транскрипте, который уже читаем через `readSessionTranscript`).

**Context Recycling Ratio** — `totalContextProduced` = сумма длин транскриптов (`JSON.stringify(lines).length`) по всем узлам дерева, включая ствол.

**Virtual Context Lifetime — новая формула + упрощённый алгоритм.**

```
virtualContextLifetime(actualTurn: number, virtualTurn: number): number
// = (actualTurn - virtualTurn) / virtualTurn
```

Формула подтверждена обратным счётом по собственному примеру tz.md («фактическая компактизация — 61-й ход; виртуальная — 34-й ход; продление жизни контекста — 79%»): `(61-34)/34 ≈ 79.4%`.

Алгоритм получения `actualTurn`/`virtualTurn` (упрощённый, без знания реального внутреннего порога компакта Claude Code — сознательно, порог не нужен, если пользоваться уже случившимся фактом):
1. Читаем реальный транскрипт ствола, находим точку компакта через уже существующий `findLastCompactBoundaryIndex` — это и есть `actualTurn` (индекс), а кумулятивная длина ствола ровно в этой точке — порог, который реально вызвал компакт (не нужно знать *почему* он сработал, только *где*).
2. Строим виртуальную кумулятивную кривую: та же последовательность хода ствола, но в каждую точку доклеена длина всех prune/sprout-веток, чьё `timestamp` в `audit.jsonl` меньше текущей точки — то есть весь «вырезанный» контент возвращается на место в момент, когда он был бы там, если бы отката/форка не было.
3. `virtualTurn` — первый индекс, где виртуальная кумулятивная кривая пересекает тот же порог (найденный на шаге 1). Виртуальный компакт неизбежно наступает раньше или одновременно с реальным (кривая только растёт быстрее или так же, никогда медленнее) — если в дереве вообще не было prune/sprout, `virtualTurn === actualTurn`, метрика = 0%, корректный вырожденный случай.

Если ствол ни разу не компактился (`findLastCompactBoundaryIndex` вернул `-1`) — VCL для этого дерева не вычисляется (`undefined`, а не 0 и не ошибка), явно помечается в отчёте как «недостаточно данных», а не молчаливый ноль.

## 5. CLI

`packages/mekiri-host/src/metricsCli.ts`, `npx tsx src/metricsCli.ts --dir <path>`. Отчёт по каждому дереву в `.mekiri/audit.jsonl` проекта + агрегат по всем деревьям сразу. DR/BC — как распределение (среднее + количество записей, не только голое число). LTS/CRR/VCL — посчитанные значения на реальных данных, с явной пометкой недостающих данных (пустое дерево, ствол без компакта) вместо деления на ноль или NaN в выводе. Human-readable текстовый вывод по умолчанию; `--json` — та же структура в JSON, для программного использования (например, будущей интеграции в `mekiri-tuning`).

## 6. Тестирование

- `sessionTree.ts`, `virtualContextLifetime` и алгоритм шагов 1-3 §4 — unit-тесты на синтетических деревьях и синтетических транскриптах (без живых вызовов SDK, без реального `.jsonl` на диске кроме временных фикстур).
- `readSessionTranscript` — тестируется на фикстурных `.jsonl`-файлах во временном `CLAUDE_CONFIG_DIR`, тем же паттерном, что уже используют live-тесты этого проекта (`writeSessionFile`/`sanitizeDir` хелперы).
- Финальная проверка — не синтетика, а реальный прогон CLI на уже накопленном `.mekiri/audit.jsonl` этого самого репозитория (там уже есть реальная, пусть и небольшая, история prune/sprout от предыдущих итераций дискофудинга) — отчёт показывается владельцу проекта как часть приёмки фичи, не только «тесты прошли».

## 7. Вне скоупа

- Интеграция метрик в `mekiri-tuning`'s Trigger B — тот скилл уже сознательно ограничен двумя простыми метриками, вычислимыми агентом вручную по одной строке лога; полный отчёт `metricsCli` — для человека, отдельная аудитория.
- Хранение/кеширование посчитанных метрик между запусками — команда всегда считает заново постфактум, дёшево при реальных объёмах `.mekiri/audit.jsonl`.
- Визуализация/графики — только текстовый и JSON вывод.
