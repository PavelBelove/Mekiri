# mekiri-gate / mekiri-tuning — design

**Дата:** 2026-07-25
**Скоуп:** два скилла для агентов, работающих внутри `mekiri-host` — `mekiri-gate` (гейт клон/субагент/инлайн, tz.md §7) и `mekiri-tuning` (протокол самонастройки `.mekiri/config.json`, core-primitive-design.md §6) — плюс wiring, без которого скиллы физически не грузятся в хостируемую сессию. Разблокированы мержем `configure_mekiri` (`7ef9044`).

---

## 1. Архитектурный гэп: skill loading wiring

`repl.ts` и `clone.ts` вызывают `query()` без `plugins`/`settingSources`/`skills` — сейчас скиллам физически неоткуда грузиться в сессию агента, которого хостит `mekiri-host`. Просто положить `SKILL.md` в целевом проекте (`--dir`) недостаточно: `mekiri-gate`/`mekiri-tuning` должны быть доступны в **любом** проекте, который хостит `mekiri-host`, а не только в этом репо.

**Решение:** локальный SDK-плагин (`SdkPluginConfig{type:'local', path}`), по той же механике, что грузит `superpowers` в эту самую CLI-сессию (`.claude-plugin/plugin.json` + `skills/<name>/SKILL.md`, автообнаружение).

**Структура:**
```
packages/mekiri-host/
  skills-plugin/
    .claude-plugin/
      plugin.json          # {name: "mekiri", description, version}
    skills/
      mekiri-gate/
        SKILL.md
      mekiri-tuning/
        SKILL.md
```

**Wiring:** оба места, вызывающие `query()` (`repl.ts`, `clone.ts`), получают
```ts
plugins: [{ type: "local", path: path.join(import.meta.dirname, "../skills-plugin") }]
```
Путь резолвится через `import.meta.dirname` (директория самого `mekiri-host`, не `--dir` целевого проекта) — так плагин работает независимо от того, какой проект хостится.

`plugin.json` — минимальный манифест (`name`, `description`, `version`), без отдельного `marketplace.json` — он нужен только для публикации через маркетплейс, здесь плагин локальный и используется только `mekiri-host`.

## 2. `mekiri-gate`

**Назначение:** гейт выбора инструмента (`prune` / `sprout` / чистый Task-субагент / инлайн-работа) — role-agnostic, применяется одинаково родителем и клоном (skill discovery не session-specific, см. `[[feedback-mekiri-prompt-layering]]`).

**Содержимое** — прямая адаптация tz.md §7.1, без добавления новых кейсов (у нас уже есть реальные эпизоды дискофудинга проекта, но решено не тащить их в скилл — table из tz.md уже покрывает контрасты):

- Вопрос 1: диспетчеризуема ли задача вообще (нужна ли коррекция курса по ходу) → если нет, инлайн, вне зависимости от актив/балласт.
- Вопрос 2: унаследованный контекст — актив или балласт → тёплый клон (актив, нужен результат, не процесс) vs чистый субагент (балласт/источник предубеждений).
- Вопрос 3 (для клона по ходу работы): контекст остаётся активом? → право на самоэскалацию (tz.md §6.3): чистый субагент на узкий вопрос изнутри клона, либо `needs_clean_look: true` в `harvest` вместо отчёта об успехе.
- Вопрос 4 (для инлайн-работы, постфактум): если кусок инлайн-работы оказался побочным эпизодом и завершён с результатом — закрыть `prune(portal)` постфактум, даже если реального выбора «клон или инлайн» в начале не было.
- Таблица контрастных примеров tz.md §7.1 — переносится как есть.

**Триггер (frontmatter `description`):** должен обеспечивать проактивную загрузку скилла перед любым нетривиальным диспетчерским решением — выбором между `prune`, `sprout`, Task-субагентом и продолжением инлайн.

## 3. `mekiri-tuning`

**Назначение:** протокол смены `.mekiri/config.json` (`sprout.depth_limit`, `sprout.parallelism`, `sprout.wait_mode`, `priorities.token_efficiency`) через `configure_mekiri`. Role-agnostic по содержимому; различие поведения парента и клона — не ветвление в тексте скилла, а следствие общего принципа (см. ниже).

### 3.1. Триггер A — явный приоритет пользователя

Пользователь прямо заявляет приоритет (например: «токены не важны, дай больше глубины/деталей», «сделай sprint глубже», «экономь токены агрессивно»). Реакция: немедленный `configure_mekiri(patch, reason: "user_override: <кратко что сказал пользователь>")`. Без отчёта и без вопроса — сам факт явного заявления уже есть согласие.

### 3.2. Триггер B — накопленный сигнал метрик

Источник — **только** `.mekiri/audit.jsonl`, прочитанный напрямую (Read/Bash), без новой инфраструктуры. Из пяти формул tz.md §12.2 в скоуп входят только две, вычислимые из одной записи лога:

- **Distillation Ratio** = `removedBranchLength / fruitLength` по каждой `prune`-записи (tz.md §12.2).
- **Branch Compression** = `branchLength / harvestLength` по каждой `sprout`-записи (tz.md §12.2).

(Lifetime Token Savings, Virtual Context Lifetime, Context Recycling Ratio — вне скоупа: требуют анализа сессионных файлов, которого у агента при чтении только `audit.jsonl` нет.)

**Плейсхолдер-пороги** (явно помечены в тексте скилла как условные, для калибровки по мере накопления реальных данных — так и задумано core-primitive-design.md §6):

| Сигнал | Порог | Источник |
|---|---|---|
| Устойчиво низкая дистилляция | ≥3 подряд `prune`-записи со средним DR < 2× | `audit.jsonl` |
| Устойчиво низкое сжатие клонов | ≥2 подряд `sprout`-записи со средним BC < 2× | `audit.jsonl` |
| Упёрлись в потолок рекурсии | `sprout` вернул `{status: "depth_limit_exceeded"}` | внутрисессионно, не из лога |

Третий сигнал — не из лога: `handleSprout` не пишет `depth_limit_exceeded` в audit (см. tools.ts:153-155), это видно только самому агенту в текущем ходе.

**Правило:** ни один сигнал из Триггера B не приводит к молчаливой правке. Реакция — короткий отчёт с конкретными цифрами (какая метрика, какое значение, за какой период) + прямой вопрос «что делаем» — тот же паттерн, каким велось обсуждение этого самого спека. Только после ответа пользователя — `configure_mekiri(..., reason: "metric_signal: <что показали цифры>")`.

### 3.3. Роль-агностичная оговорка про клонов

Шаг «спросить» требует живого контакта с пользователем прямо сейчас. Это не ветвление «если ты клон» (запрещено правилом role-agnostic skills, см. `[[feedback-mekiri-prompt-layering]]`), а общий принцип: **действуй по нему исходя из того, есть ли у тебя сейчас канал к пользователю, а не исходя из своей роли**.

- Есть контакт (типично — родитель в интерактивном REPL): спросить напрямую, как в 3.2.
- Нет контакта (типично — клон, работающий автономно до `harvest`): не применять правку самостоятельно. Вынести наблюдение в свой обычный `harvest`-результат (не как отдельный внеплановый отчёт, а как часть возвращаемого дистиллята), оставив решение тому, у кого есть контакт с пользователем.

Триггер A (явный приоритет) в этой оговорке не нуждается: если пользователь прямо сказал что-то клону через `task`, это уже прошло через родителя при вызове `sprout` — контакт уже состоялся.

## 4. Тестирование и валидация

**Wiring (код, тестируется как код):**
- Юнит: валидность `plugin.json` (обязательные поля), валидность фронтматтера обоих `SKILL.md` (`name`, `description`).
- Live smoke-тест (по образцу `77bb406` для `configure_mekiri`): реальный `query()` с `plugins`, подтверждение, что `mekiri-gate`/`mekiri-tuning` видны агенту (через `Skill`-тул или список доступных скиллов в системном сообщении) — и в `repl.ts`, и в `clone.ts` (клон наследует тот же `plugins`, но это отдельная сборка опций, стоит проверить явно, а не полагаться на аналогию с родителем).

**Содержимое (проза, не тестируется юнитами):**
- Реальный dogfooding, а не «тестовая фаза» — по стандарту проекта (см. `[[feedback-dogfood-asap]]`): применить `mekiri-gate` на реальном диспетчерском решении в текущей работе над Mekiri; реально прогнать оба триггера `mekiri-tuning` — включая Триггер B на уже накопленном `audit.jsonl` этого репо (там уже есть реальные `prune`/`sprout`/`configure_mekiri` записи от предыдущих итераций).

## 5. Вне скоупа этой итерации

- Системный промпт-слой `mekiri-host` (`query()` без кастомного system-prompt addition) — отдельный, уже зафиксированный гэп, не тянем сюда (см. `[[feedback-mekiri-prompt-layering]]`).
- Lifetime Token Savings / Virtual Context Lifetime / Context Recycling Ratio в `mekiri-tuning` — требуют анализа сессионных файлов, не только `audit.jsonl`.
- Публикация `skills-plugin` как отдельного маркетплейс-плагина (`marketplace.json`) — не нужно, плагин используется только `mekiri-host` локально.
- Калибровка реальных числовых порогов Триггера B по накопленным данным — пороги в этой итерации плейсхолдерные по дизайну (core-primitive-design.md §6).
