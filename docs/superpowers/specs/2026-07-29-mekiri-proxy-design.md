# Дизайн: `mekiri-proxy` — прокси-подрезка на проводе для любой сессии Claude Code

**Проект:** Mekiri
**Статус:** спек, обсуждён и одобрен пользователем, self-review пройден
**Контекст:** [whitepaper.md](../../../whitepaper.md), [tz.md](../../../tz.md), [wire-prune-findings.md](../../../wire-prune-findings.md) (эмпирическая проверка на реальном API, дважды, кеш переживает срез хвоста на уровне HTTP-запроса), `packages/mekiri-core` (переиспользуется почти без изменений), `packages/mekiri-host` (архитектурный тупик для этой цели — см. §0, остаётся в `main` только как справочник паттернов до готовности этого пакета)
**Скоуп:** новый пакет `packages/mekiri-proxy`, дающий **любой** существующей сессии Claude Code (прежде всего — основной пользовательской сессии, не отдельному REPL) настоящие `prune`/`sprout`/`configure_mekiri` через переписывание HTTP-трафика на проводе, без изменения того, что видит пользователь в интерфейсе.

**Вне скоупа этой итерации:** публичный npm-релиз (альфа только для локальной установки, друзей-разработчиков — см. §7); ACP-адаптер; `interrogate`-режим; `promote`; адаптация `metricsReport`/`sessionTree` под плоское дерево сессий (дерево сейчас строится на паре parent/child `session_id`, у `prune` в новой модели этой пары больше нет — оставлено отдельным пунктом бэклога, не блокирует этот пакет).

---

## 0. Почему не `mekiri-host`

Предыдущая архитектура (`packages/mekiri-host`) предполагала, что "стволом" Mekiri является отдельный REPL, сам владеющий циклом `query()` Agent SDK — это дало настоящий `prune`/`sprout`, но ценой того, что пользователь должен запускать *другой* процесс вместо своей обычной сессии Claude Code/IDE-плагина. Реальный, самый ценный "ствол" проекта — именно основная пользовательская сессия (самая долгоживущая, получающая больше всего фидбека, накапливающая больше всего контекста), а не отдельный тестовый REPL. `mekiri-host` для этой цели структурно не годится и будет заархивирован в git-ветку **после того**, как этот пакет заработает — код `mekiri-host` не переиспользуется напрямую, но три его паттерна переносятся мыслью: рамка клона ("ты клон, задача завершена после report'а"), осознанное решение не ограничивать самоэскалацию `depth_limit` жёстче аудит-лога, анти-нытьё в сигнале тюнинга.

---

## 1. Архитектура: два процесса, один кодбейз

- **daemon** — долгоживущий процесс, слушает `127.0.0.1:PORT` (дефолт 8791, конфигурируемо). Держит HTTPS-релей на `api.anthropic.com` (форвардит все заголовки как есть, включая реальный `authorization`/OAuth подписки) + in-memory **и на диске** карту `sessionId → активное правило среза` + внутренний control-API поверх того же HTTP-сервера (`POST /control/prune`, `POST /control/sprout-register`).
- **mcp-server** (stdio) — спавнится Claude Code per-сессию через `.mcp.json` в проекте. При старте: читает `process.env.CLAUDE_CODE_SESSION_ID` (свой `session_id` — подтверждено эмпирически, переменная реально присутствует в окружении процесса Claude Code) и `process.cwd()` (свой `dir`); идемпотентно проверяет демона тем же паттерном, что уже проверен в `.claude/skills/mekiri-orchestrator/scripts/ensure-running.sh` (матчить реальный процесс по `pgrep -f` с регэксп-экранированием пути, не доверять протухшему pidfile) — если не жив, поднимает detached; если жив — просто открывает HTTP-соединение к нему. Отдаёт модели тулы `prune`/`sprout`/`configure_mekiri`.

**Жёсткое требование к кешу** (сформулировано пользователем в обсуждении): у ствола, всех клонов и всех откаченных веток должен быть **byte-identical** набор MCP-тулз — иначе блок `tools` в запросе (часть кешируемого префикса) расходится и кеш рвётся. Практическое следствие: один и тот же `.mcp.json` на проект, без вариаций конфига между вызовами.

### Переиспользование `mekiri-core` без изменений кода
`findBoundary`/`readSessionTranscript` (цитата → `messageId` из реального `.jsonl` на диске — ровно то, что нужно для превращения цитаты агента в индекс сообщения при срезе на проводе), `validateFruit`, `configSchema`/`configStore`, `auditLog` (одно изменение схемы — см. §4), `quoteMatcher`, `fruitSchema`.

## 2. Идентификация сессии на проводе

Реальное тело запроса, отправляемого Claude Code, содержит `metadata.user_id` — JSON-строку с полями `device_id`, `account_uuid` и **`session_id`** (подтверждено чтением дампа реального запроса). Демон парсит это поле на каждом входящем запросе и однозначно знает, какой сессии он принадлежит — без файловых эвристик, устойчиво к нескольким параллельным сессиям на одной машине/проекте.

---

## 3. Схемы тулз

```ts
prune({
  quote: string,
  note_type: "portal" | "death_reload",
  fruit: unknown,              // валидируется validateFruit, как сейчас
  keep_code: boolean,
})
→ { status: "ok", cut_effective_from: "next_request" }
  | { status: "ambiguous", occurrences: number }
  | { status: "not_found" }
  | { status: "in_compacted_zone", last_compact_message_id: string }
  | { status: "invalid_fruit", errors: string[] }

sprout({
  task: string,                // обёрнут той же рамкой "ты клон...", что уже в mekiri-host
  wait_mode?: "sync" | "async", // default "sync"
})
→ { status: "ok", child_session_id: string, result: string, harvested_implicitly?: true }
  | { status: "pending", child_session_id: string }   // wait_mode: "async"
  | { status: "depth_limit_exceeded" }

configure_mekiri({
  patch: Partial<MekiriConfig>,
  reason: string,
})
→ { status: "ok" } | { status: "invalid", errors: string[] }
```

Сигнатуры `prune`/`sprout`/`configure_mekiri` **намеренно совпадают** с текущими `mekiri-host`-тулзами — решающая логика в `mekiri-gate`/`mekiri-tuning` почти не требует переписывания, меняется реализация под капотом, не то, что видит модель.

## 4. Поток данных

### `prune`
1. `validateFruit` — невалидно → ошибка агенту, до демона не доходит.
2. `readSessionTranscript(dir, свой session_id)` → `findBoundary(transcript, quote)`. Не `ok` → ошибка агенту, ничего не регистрируется.
3. Считаем `removedBranchLength`/`fruitLength` (как сейчас), рендерим `fruit` в текст дистиллята (тот же формат полей, что мekiri-host уже пишет: portal — summary/files_touched/gotchas; death_reload — tried/ruled_out/facts_learned).

   **Открытый технический вопрос, не решённый на уровне спеки, только на синтетическом тесте**: `findBoundary` отдаёт `messageId` — UUID из локального `.jsonl`-транскрипта. Демон же режет `messages[]` из реального API-запроса, где записи — plain Anthropic Messages формат, не обязательно 1:1 с записями транскрипта (system-reminder вставки, thinking-блоки, пары tool_use/tool_result могут считаться иначе). В эмпирической проверке (`wire-prune-findings.md`) это не проверялось — там резался чистый текстовый диалог по известному заранее индексу. Первая задача в плане реализации — проверить живьём, как `messageId` из транскрипта сопоставляется с позицией в `messages[]` реального запроса при наличии тул-вызовов, и только затем писать логику среза; если прямого соответствия нет, понадобится сопоставление по содержимому/порядку, а не по голому индексу.
4. `POST /control/prune {sessionId, dir, keepFromMessageId, distillate}` → демон **перезаписывает** (не копит) активное правило для этой `sessionId`. Что оставить от прошлого дистиллята при повторном prune — решает агент, когда пишет новый `fruit` (ретроактивное поглощение — авторское решение, не механика демона).
5. Аудит-запись `prune` (см. §5, без `newSessionId`).
6. Ответ: срез вступает в силу **со следующего исходящего запроса** этой сессии — текущий ход агент дочитывает как есть, ничего из уже увиденного не пропадает задним числом.

### `sprout`
1. Свой `session_id`/`dir`/глубина (глубина — см. ниже).
2. Спавн настоящего `claude --resume <свой session_id> --fork-session -p "<framed task>" --output-format json`, с `ANTHROPIC_BASE_URL` на тот же демон и тем же `cwd` — тот же `.mcp.json` применяется автоматически, клон **сам** получает свой mcp-server и, следовательно, сам умеет `prune`/`sprout` без единой дополнительной настройки.
3. Транзиентная гонка "сообщение ещё не долетело на диск" — тот же ретрай-паттерн, что уже в `mekiri-host` (`[50,100,200,400]ms`), только теперь это ретрай запуска дочернего процесса, а не внутреннего SDK-вызова.
4. `wait_mode: "sync"` — ждём завершения, парсим `result` как harvest. `"async"` — возвращаем `{status:"pending", child_session_id}` сразу, а harvest прилетает родителю позже тем же каналом, что уже проверен в `mekiri-host` (инъекция в очередь ввода).
5. Аудит-запись `sprout` (childSessionId — реальный id форкнутой ветки).
6. **Глубина рекурсии**: родитель передаёт клону `MEKIRI_SPROUT_DEPTH=<свой+1>` через env дочернего процесса (по умолчанию 0 — я ствол). Клон при старте сверяет со `sprout.depth_limit` из общего `.mekiri/config.json`.

### `configure_mekiri`
Чистая файловая операция (`applyConfigPatch`/`saveConfig` в `.mekiri/config.json`) + аудит-запись — демон не участвует вообще.

---

## 5. Формат аудит-лога

Единственное изменение схемы относительно `mekiri-core`'s текущего `PruneAuditEntry`: поле **`newSessionId` становится необязательным** (в новой модели `prune` не создаёт новую сессию — сессия остаётся той же, меняется только то, что уйдёт по проводу следующим запросом). Для `prune`-записей, порождённых этим пакетом, поле просто отсутствует. `SproutAuditEntry`/`ConfigureAuditEntry` — без изменений.

---

## 6. Персистентность и обработка ошибок

- **Активные правила среза персистятся на диск** (`.mekiri/proxy-rules.json`, ключ — `sessionId`), демон подгружает их при старте. Без этого падение/перезапуск демона молча теряет все активные срезы — следующий запрос улетит полной непорезанной историей без единой ошибки, только неожиданно возросшей ценой. Персистентность делает симметричным восстановление и после падения демона, и после `--resume` сессии на следующий день после перезагрузки машины.
- Демон недоступен / не поднялся (порт занят, нет прав) → mcp-server отдаёт агенту явную ошибку тула с таймаутом на control-запрос, не виснет.
- Гонка первого запуска (Claude Code читает `ANTHROPIC_BASE_URL` при своём старте, демон поднимается следом за спавном MCP-процесса) — не считается блокером дизайна (обычные HTTP-клиенты ретраят обрыв соединения), но **явно вынесено в план на проверку живьём**, не принимается на веру.
- Проекты без `ANTHROPIC_BASE_URL`/`.mcp.json` — не затронуты вообще, это opt-in per-проектная настройка.

## 7. Тестирование и распространение

- `mekiri-core` — без изменений, кроме адаптации существующих тестов под необязательный `newSessionId`.
- Новый пакет: юнит-тесты на чистую функцию среза (`messages[] + rule → messages[]`) и на разбор `session_id` из `metadata.user_id` — без сети.
- Демон тестируется против **поддельного upstream-сервера** (мок вместо `api.anthropic.com`) — основной набор тестов не требует реального API-ключа и не зависит от него на чужой машине/CI.
- Отдельный, явно опциональный **живой smoke-тест** против настоящего API — включается вручную флагом, не часть обычного прогона (реальные деньги + чувствительность ToS, см. `wire-prune-findings.md` §3).
- `depth_limit` через env — тест на отказ клона превышать лимит.
- **Распространение на этом этапе**: только локальная установка через git-клон этого репозитория (без публичного npm-релиза — механизм переписывает трафик подписки, публичный релиз сейчас непропорционально большое обязательство). Целевая аудитория — альфа-тестеры, разработчики с собственными агентами. Требование к README/установочным инструкциям в репозитории: **самодостаточность** — агент на чужой машине, без памяти этой сессии, должен суметь поставить и настроить пакет, руководствуясь только тем, что лежит на GitHub.
