# Дизайн: mekiri-host, минимальная итерация (prune-only, без ACP)

**Проект:** Mekiri
**Статус:** спек, ожидает ревью пользователя
**Контекст:** [whitepaper.md](../../../whitepaper.md), [tz.md](../../../tz.md), [2026-07-24-core-primitive-design.md](2026-07-24-core-primitive-design.md) (полная целевая архитектура), `packages/mekiri-core` (реализован и одобрен)
**Скоуп:** минимально жизнеспособный хост — только `prune`, без ACP, без `sprout`. Явная цель — начать реальное догфудирование как можно раньше (см. память `feedback_dogfood_asap`), а не построить полную архитектуру за один присест. ACP-адаптер и `sprout` — следующая итерация(и).

---

## 1. Почему именно так урезано

Полная целевая архитектура (ACP-адаптер поверх `claude-agent-acp`, обе тулзы, host как универсальный ACP-агент) описана в `2026-07-24-core-primitive-design.md` и остаётся целью. Но она требует заметного объёма интеграционной работы (форк/расширение стороннего ACP-пакета) прежде чем что-либо станет реально используемым. Раз приоритет — начать пользоваться инструментом в разработке самого Mekiri как можно раньше, эта итерация сознательно жертвует универсальностью фронтенда ради самого быстрого пути к «`prune` реально режет мою собственную сессию».

**Что отложено на следующую итерацию:** ACP-адаптер (форк `claude-agent-acp`), тулза `sprout`/`harvest`, конфиг-driven `wait_mode`/`parallelism` (не нужны без `sprout`), скиллы `mekiri-gate`/`mekiri-tuning`.

## 2. Архитектура

```
packages/mekiri-host/
  src/
    repl.ts            # stdin/stdout цикл поверх query()
    liveTranscript.ts   # накопление RawLine-совместимого массива из потока SDKMessage
    tools.ts             # in-process MCP-тулза prune (createSdkMcpServer)
    index.ts             # CLI entrypoint (--resume, --dir)
  test/
    repl.smoke.test.ts   # 1-2 живых smoke-теста
```

Зависит от `mekiri-core` (`validateFruit`, `findBoundary`, `findLastCompactBoundaryIndex`, `createBranch`, типы) и `@anthropic-ai/claude-agent-sdk` (`query`).

### 2.1. REPL-цикл

Простой терминальный чат: читает строку из stdin как `prompt` для `query()`, стримит текстовые куски ответа в stdout, ждёт следующую строку. CLI-флаги:
- `--resume <session-id>` — подхватить существующую сессию (в т.ч. текущую VS Code-сессию, если её id известен) вместо старта с нуля.
- `--dir <path>` — рабочая директория проекта для `forkSession`/`query()`; по умолчанию `process.cwd()`.

Никакого ACP, никакого JSON-RPC — прямой вызов SDK.

### 2.2. Живой адаптер транскрипта (`liveTranscript.ts`)

`query()` отдаёт поток `SDKMessage` — union из полутора десятков типов, куда более богатый, чем плоский jsonl-формат, на котором построен `mekiri-core`. Но:

- **`SDKAssistantMessage.message`** — это `BetaMessage` (тот же формат, что и Anthropic Messages API), и его `content`-блоки (`{type:"text", text}`, `{type:"thinking",...}` и т.д.) структурно совпадают с тем, что уже потребляет `findBoundary` из `mekiri-core` — адаптации самого текста не требуется.
- **`parentUuid`** не читается ни `findBoundary`, ни `findLastCompactBoundaryIndex` (проверено по факту реализации в `mekiri-core`) — адаптеру не нужно восстанавливать реальную родительскую цепочку, можно оставлять `null`.
- **`isSidechain`** всегда `false` для всего, что приходит через основной поток `query()` — субагентские (sidechain) сообщения физически не попадают в этот поток на уровне SDK, они изолированы в отдельном под-цикле и возвращаются только как готовый результат тулзы. Раз `mekiri-core`'s фильтр `isSidechain` рассчитан на архивный jsonl, где sidechain-строки физически перемешаны с основными, а здесь такого смешения по конструкции нет — поле можно жёстко проставлять `false`.
- **`SDKCompactBoundaryMessage`** — отдельный тип сообщения в потоке, ровно сигнализирующий то же событие, которое в архивном jsonl закодировано парой `system`+`compactMetadata`/`user`+`isCompactSummary`. Адаптер транслирует его в ту же двухстрочную RawLine-пару, чтобы `findLastCompactBoundaryIndex` работал без изменений.

Host держит один растущий `RawLine[]`-массив на текущую живую сессию; при перезапуске на новую ветку (после `prune`) массив обнуляется.

### 2.3. `prune`-тулза и переключение ветки

`createSdkMcpServer` регистрирует `prune(quote, note_type, fruit, keep_code)` (схема — из `mekiri-core`, `validateFruit`). Хендлер:
1. Валидирует `fruit` через `validateFruit`.
2. Резолвит `quote` через `findBoundary(liveTranscript, quote)`.
3. При `status:"ok"` — `createBranch({branchType:"prune", sessionId: current, upToMessageId: uuid, ...})` из `mekiri-core` (реальный `forkSession`, локальная файловая операция).
4. Хост останавливает потребление старого `query()`-итератора (`.return()`), обнуляет `liveTranscript`, стартует `query({resume: newSessionId, forkSession: true, prompt: injectText})`, REPL продолжает с новым генератором.
5. Ошибочные статусы (`not_found`/`ambiguous`/`in_compacted_zone`) возвращаются агенту как обычный tool_result — без побочных эффектов.

Никакого `report`/`configure_mekiri` в этой итерации — только `prune`, поэтому инвариант «набор тулз одинаков на всех ветках» (design spec §2) тривиально выполняется сам по себе (одна тулза, всегда одна и та же).

## 3. Тестирование

Живые вызовы `query()` стоят реальные токены — по решению пользователя, тестовый бюджет сознательно минимален:

- **1-2 дешёвых smoke-теста** (`test/repl.smoke.test.ts`): максимально короткий реальный `query()` (промпт вроде «ответь одним словом: ok»), проверяющий сам механизм остановки старого итератора и старта нового после программного вызова, эквивалентного `prune` — не полный сценарий с реальным LLM-вызовом `prune`-тулзы (это дороже и менее детерминированно), а прямая проверка `liveTranscript`-накопления и переключения генератора.
- **Остальное — ручное догфудирование**: как только REPL и `prune` реально работают, дальнейшая разработка самого Mekiri ведётся через этот REPL (с `--resume` текущей сессии, где применимо), и баги фиксятся или уходят в план по ходу реальной работы — не через дополнительные автотесты.

---

## 4. Вне скоупа этой итерации

- ACP-адаптер (форк `claude-agent-acp`) — отдельная итерация.
- `sprout`/`harvest` — отдельная итерация (после того как `prune` подтвердит себя на практике).
- `configure_mekiri`, `wait_mode`/`parallelism` — не нужны без `sprout`.
- Скиллы `mekiri-gate`/`mekiri-tuning` — привязаны к наличию обеих тулз и конфига, откладываются вместе с ними.
- Пре-компактный снапшот (tz.md §8) — из design-спека мыслится как часть полного host, здесь не реализуется.
