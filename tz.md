## 1. Архитектура: один примитив, два параметра

То, что выглядит как «два разных тулза», концептуально — один примитив с двумя независимыми битами настройки; это описывает интерфейс, видимый агенту, а не то, как каждый бит на самом деле реализован (см. ниже):

```
spawn(transcript_slice, injected_message, kill_source: bool, timing: proactive | reactive)
```

- `kill_source` — уничтожается ли исходная сессия (prune) или остаётся жить параллельно (sprout).
- `timing` — вызывается ли spawn до того, как агент начнёт грязную работу (проактивно, потому что заранее понимает, что испачкается), или после того, как грязь уже накопилась (реактивно, по факту).

Содержательных комбинаций три:

| kill_source | timing | Сценарий |
|---|---|---|
| да | реактивно | Откат. Ветка уже отработала своё, держать её живой незачем. |
| нет | проактивно | Тёплый клон. Родитель продолжает главную задачу, клон уходит в сторону. |
| нет | реактивно | Редкий пограничный случай: ветка загрязнена, но родителю зачем-то нужно параллельно доработать что-то в старом терминале, пока новый стартует с чистого среза. Механизм не запрещает. |
| да | проактивно | Не отдельный случай, а отложенное решение: «знаю, что испачкаюсь, но почищу потом» — это просто откат, вызванный позже по факту. |

**Следствие для того, что видит агент.** Неважно, через какую дверь агент вошёл — реактивно откатившись или проактивно форкнувшись, — результат с его точки зрения структурно один и тот же: «новая» точка продолжения, порождённая от дистиллята, с наследованным контекстом до бита. Заметка при откате и задача при форке — поля одного типа объекта, доставляемого в хвост (см. §6).

**Расхождение на уровне реализации.** На Claude Code эти два значения `kill_source` исполняются двумя принципиально разными механизмами, и это не историческая случайность, а следствие того, что откат и форк ставят разные требования:

- `kill_source: true` (откат, prune) не обязан порождать новую сессию вообще — обрезаемая ветка умирает безвозвратно, значит достаточно, чтобы *будущие* запросы к модели этой ветки её не видели. Это дешевле честного форка: не нужен новый процесс, новый session-id, копирование префикса. Реализовано как перезапись на уровне HTTP-прокси (см. §2) — исходный файл сессии не трогается вообще, ни разу.
- `kill_source: false` (тёплый клон, sprout) обязан оставить родителя живым и продолжающим свой ход независимо от клона — а значит клону нужен собственный, честно форкнутый процесс с собственным session-id. Здесь дешёвого пути нет: это буквальный форк (см. §2).

Следствие: у отката больше нет «дерева сессий» в смысле файлов — есть один и тот же файл сессии на всё время жизни родителя, история которого просто выглядит по-разному в каждом следующем запросе к API. Явный дискриминатор `branch_type` в метаданные ветки больше не пишется — писать его было нечему и некуда: для prune нет новой ветки-файла, которую нужно было бы отличить от sprout-ветки; для sprout сам факт нового session-id уже однозначно отличает его от родителя. Аудиторский след живёт не в транскрипте, а в `rule_id` записи (см. §6.1, §6.4).

## 2. Работа с транскриптом (исполнительный слой для Claude Code)

Сессии Claude Code лежат в `~/.claude/projects/<hash>/<session-id>.jsonl`, одно сообщение — одна jsonl-строка. Но prune и sprout работают с этим файлом принципиально по-разному.

**Откат (prune) — переписывание на уровне HTTP-прокси, без форка сессии.**

- `mekiri-proxy` — локальный HTTP-демон, единый на машину (не на проект), поднимаемый через переменную `ANTHROPIC_BASE_URL`: Claude Code отправляет каждый исходящий `/v1/messages` через него вместо прямого похода в API.
- Тулза `prune` не создаёт новую сессию и не трогает jsonl-файл транскрипта вообще. Вместо этого она регистрирует в демоне правило `{id, matchQuote}` (control-запрос, см. §4); демон хранит правила в общем файле `~/.mekiri-proxy/rules.json`, ключ — `sessionId`, файл переживает перезапуск самого демона.
- На каждый следующий запрос той же сессии демон вычисляет её `sessionId` из тела запроса и заново — без предпосчитанного индекса — ищет диапазон для вырезания прямо в актуальном массиве `messages[]` этого конкретного запроса: начало — по тексту цитаты в assistant-сообщении, конец — по паре `tool_use`/`tool_result` самого вызова prune, опознанной по `rule_id`, эхом возвращённому в `tool_result` (не по тексту — иначе два похожих по смыслу отката было бы не различить). Правила накопительные и разрешаются независимо друг от друга против полного массива на каждый запрос: более поздний и более широкий откат «бесплатно» поглощает якорь более раннего, если его диапазон его перекрывает.
- Локальный файл сессии и то, что видит пользователь в интерфейсе, не меняются никогда — переписывание существует только на уровне байтов, уходящих в API. Для пользователя история выглядит нетронутой; для модели, отправляющей следующий запрос, — обрезанной.
- Дистиллят (`fruit`) не инжектится текстовым сообщением в хвост — вместо этого он пишется в дисковый архив (`.mekiri/sessions/<id>/report.md` + `capsule.md`, общий по проекту индекс `.mekiri/capsule-index.jsonl`) и остаётся доступен через `graft` независимо от того, что происходит с самой веткой дальше (см. §6.4, §6.5).

**Тёплый клон (sprout) — буквальный форк.**

- `sprout` по-прежнему форкает реальную сессию: headless-подпроцесс `claude --resume <sessionId> --fork-session -p "<задача>" --output-format json`, синхронно завершающийся, когда клон допечатал финальный ответ в print-режиме; его JSON stdout (`{session_id, result}`) и есть дистиллят, никакого отдельного шага харвеста не требуется.
- Клон запускается с тем же `ANTHROPIC_BASE_URL`, указывающим на тот же демон — значит уже наложенные родителем правила отката применяются и к унаследованному контексту клона: клон видит ту же обрезанную историю, что увидел бы родитель на своём следующем запросе.
- Перезапуск через `--resume` сохраняет префикс байт-в-байт → кеш переживает рестарт процесса, пока диапазон отката к этому префиксу не применяется.

## 3. Адресация границы: дословная цитата

Агент не видит внутренние id сообщений — но видит собственный текст. Поэтому граница задаётся дословной цитатой: агент копирует первое предложение СВОЕГО хода (8–10 слов — компактно и почти всегда уникально), с которого начинается мусор.

Это операция чтения, а не вспоминания: текст физически лежит в контексте, агент его копирует. Риск не в способности воспроизвести текст точно (модели надёжно копируют даже сложные последовательности), а в привычке перефразировать «по смыслу» — лечится протоколом ретрая:

- Точное уникальное вхождение → граница = вся jsonl-строка, режем включительно.
- Ноль вхождений → `not_found`, просьба скопировать дословно.
- Больше одного → `ambiguous`, просьба дать более длинную или другую цитату.
- Цитата в компактизированной зоне → `in_compacted_zone` (см. §5).

Никаких эвристик «берём последнее вхождение». Молчаливая обрезка не в том месте — худший из отказов: агент даже не узнает, что живёт в неправильной ветке.

**Момент разрешения границы — дважды, с разным смыслом.** В момент вызова `prune`/`tag` граница проверяется один раз против локального транскрипта — только чтобы сразу вернуть агенту `not_found`/`ambiguous`/`in_compacted_zone`, если цитата плохая. Но для собственно вырезания эта проверка не переиспользуется как готовый индекс: настоящая позиция среза каждый раз ищется заново, против того конкретного `messages[]`, который в этот момент реально уходит в API (см. §2) — потому что номер строки, посчитанный один раз по локальному jsonl, не обязан совпадать с позицией в живом массиве запроса. Совпадение по содержимому, а не по заранее вычисленному номеру — единственный надёжный якорь.

**Вложенные откаты.** Ничто не мешает границе более позднего отката лежать раньше уже вписанных заметок от предыдущих мелких откатов той же ветки — тогда один вызов «съедает» сразу несколько эпизодов, схлопывая их в одну финальную заметку. Это не отдельный режим, а естественное следствие того, что откат всегда режет по дословной цитате в текущем транскрипте, а не по номеру предыдущего отката, и что правила разрешаются независимо друг от друга на каждый запрос (см. §2). Практический сценарий — частая мелкая гигиена по ходу побочного эпизода плюс один более крупный откат в его конце, см. [whitepaper.md §4.1](whitepaper.md#41-почему-дистилляция-при-откате-качественно-лучше-компактизации).

## 4. Канал команд

Два варианта в зависимости от исполнительного слоя:

- **Claude Code (текущая реализация).** Агент вызывает MCP-тулзу; тулза шлёт control-запрос (`POST /control/rule`) локальному HTTP-демону `mekiri-proxy` и сразу возвращает ответ агенту — никакой синхронизации по hook `Stop` не требуется, потому что откату нечего синхронизировать: сессия не перезапускается, значит нет паузы «дождаться конца хода перед пересозданием файла». Правило начинает действовать со следующего же исходящего запроса той же сессии (`cut_effective_from: "next_request"`, см. §6.1) — без задержки, без ожидания. Демон при этом bytes-level: он инспектирует и переписывает тело `/v1/messages` до пересылки в реальный API, полностью буферизуя запрос (заголовок `transfer-encoding` снимается, `content-length` пересчитывается заново, чтобы не спровоцировать request smuggling).
- **ACP (целевая архитектура, см. [whitepaper.md §7](whitepaper.md#7-позиционирование-относительно-agent-client-protocol)).** Тот же MCP-вызов, но канал — MCP-over-ACP, который предоставляет прокси-компонент, сидящий между клиентом и агентом. С точки зрения агента прокси и есть клиент, поэтому легальная петля выглядит как «агент просит через тулзу → прокси, будучи формально клиентской стороной, вызывает штатный протокольный метод сессии». Текущий bytes-level демон — рабочий суррогат этой архитектуры, а не она сама: он существует потому, что ACP `session/fork` пока не принят и не стабилен, а не потому что HTTP-перехват — целевое решение.

## 5. Взаимодействие с компактизацией

Компактизированная часть контекста — уже дистиллят; откатываться «внутрь» неё бессмысленно семантически (там нечего чистить) и опасно технически (цитаты из съеденных ходов не найдутся). Правила:

- **Зона отката = только сырые ходы после последней компактизации.** Проверка находит последнее compact-событие в транскрипте; всё до него — read-only для адресации цитатой (см. §3).
- После компактизации агент теряет доступ к точкам отката, лежавшим до неё — старые `rule_id` не исчезают (они по-прежнему переписывают то, что от них осталось), но ссылаться на что-то внутри уже съеденной компактом зоны новым вызовом `prune`/`tag` больше нельзя.
- Автокомпакт не отключается. Он аварийный клапан и остаётся штатным. Откаты лишь понижают его с рутины до редкого события — а поскольку откат не создаёт нового файла сессии, ему нечего терять при компакте: правила продолжают действовать на том же файле, что и раньше.

**Уточнение риска «повторного захода в тупик».** Важно не путать механизм с человеческой моделью «забыл и повторил путь» — после отката это не забывание, а структурно другой хвост той же сессии. Риск не в забывании, а в том, что ствол контекста детерминирует стартовую точку: тот же тикет, тот же код, тот же системный промпт с высокой вероятностью статистически сходятся к тому же выводу заново — не потому что «помнят» путь, а потому что стартуют с тех же приоров. `ruled_out` в death_reload-заметке — не инструкция «не ходи туда снова», а факт, специально вписанный, чтобы возмутить эту дефолтную сходимость (см. CDCL-аналогию, [whitepaper.md §6](whitepaper.md#6-генеалогия-и-наследование-ламарк-не-эволюция)).

## 6. Спецификация тулз

Четыре MCP-тулзы. `prune` и `sprout` доставляют новый контент в хвост (общий по природе объект — заметка или задача); `tag` и `graft` работают с дисковым архивом дистиллятов и ничего не переписывают в живом транскрипте.

### 6.1. `prune(quote, note_type, fruit, keep_code)`

```
prune(
  quote:      string,   # дословная цитата начала первого выбрасываемого хода
  note_type:  "portal" | "death_reload",
  fruit:      { ... },  # схема зависит от note_type — то, что остаётся после обрезки
  keep_code:  bool      # true (типовой случай): файлы проекта не откатываются
)
```

Критично: заметка пишется ДО отката, тем же вызовом. Она — аргумент тулзы, сформулированный в момент полного понимания. После отката понимания уже нет, писать некому.

**`note_type: portal`** — побочная работа завершена успешно, ветка добровольно сворачивается в факт:
- `summary` — что сделано и почему (обязательное);
- `files_touched` — список изменённых файлов + суть правок (обязательное при `keep_code: true`): после отката агент не видит диффов, и обязан знать, что его знание об этих файлах устарело — при следующем обращении файл перечитывается, а не правится по памяти о старой версии;
- `gotchas` — грабли, на которые наступил.

**`note_type: death_reload`** — гипотеза не подтвердилась, попытка провалилась:
- `tried` — что именно пробовал;
- `ruled_out` — что теперь исключено и почему (обязательное — единственное, что возмущает детерминированную сходимость к тому же тупику, см. §5);
- `facts_learned` — установленные попутно факты;
- `trigger` — `self_detected | user_feedback` (необязательное, но рекомендованное). На практике death_reload чаще вызывается не внутренней рефлексией, а прямым отрицательным фидбеком пользователя в живой сессии («ты всё понял не так, ты сломал X») — см. [whitepaper.md §4](whitepaper.md#4-игровая-метафора-суперспособности-недоступные-человеку). Такой `ruled_out` несёт информацию, которую агент не мог бы вывести сам из собственного контекста, и его ценность для возмущения детерминированной сходимости выше, чем у самодиагностированного тупика — стоит различать источник, а не сваливать оба случая в одну заметку без пометки.

Заметка (`fruit`) не дописывается служебным блоком метаданных в транскрипт — она уходит в дисковый архив (`recordDistillate`, см. §2 и §6.4/6.5) под сгенерированным `rule_id`, который и есть весь «дискриминатор ветки», нужный постфактум.

Ответ `ok` возвращает `{ rule_id, cut_effective_from: "next_request" }` — явное предупреждение агенту, что уже отправленный этим самым ответом ход ещё не обрезан: обрежется только следующий исходящий запрос той же сессии (см. §2, §4). Прочие ответы: `not_found | ambiguous | in_compacted_zone`.

### 6.2. `sprout(task, wait_mode?)`

```
sprout(
  task:       string,           # новая главная задача клона, дописывается в конец копии контекста
  wait_mode:  "sync" | "async"  # необязательное, из .mekiri/config.json по умолчанию
)
```

- Реализация — headless-подпроцесс `claude --resume <sessionId> --fork-session -p "<task>" --output-format json` (см. §2); его JSON stdout `{session_id, result}` возвращается родителю как `tool_result` — отдельной тулзы завершения клона («harvest») не существует, подпроцесс сам завершается, когда клон допечатал финальный ответ.
- Глубина рекурсии ограничена не аргументом тулзы, а `sprout.depth_limit` в `.mekiri/config.json`, передаётся вниз клону через переменную окружения и проверяется перед запуском подпроцесса.
- `wait_mode: "async"` присутствует в конфиг-схеме, но **пока не реализован**: вызов с ним отклоняется статусом `async_not_supported` — честное ограничение сегодняшнего дня, а не описание будущей возможности как готовой.
- Форк — немедленный: «здесь и сейчас», пока кеш горячий. При транзиентной ошибке форка (гонка с ещё не сброшенным на диск транскриптом) — ретрай с бэкоффом `[50, 100, 200, 400]` мс.
- Префикс клона байт-в-байт равен родительскому на момент форка, включая уже применённые к родителю правила отката (см. §2). Рекурсия: клон может клониться и откатываться, но наверх всегда возвращается только дистиллят.

### 6.3. Право клона на самоэскалацию

Контекст, унаследованный клоном, может из актива стать балластом по ходу работы — не только в момент выбора инструмента. Если клон изнутри форкнутой ветки замечает признаки хождения по кругу (те же тупики, что и триггер death_reload в §5), это сигнал, что унаследованное понимание стало источником предубеждения прямо во время работы. Два легитимных выхода:

- эскалировать и вызвать внутри себя чистого субагента на узкий вопрос («правда ли баг там, где я думаю»);
- вернуть родителю не результат, а рекомендацию «нужен чистый взгляд» вместо отчёта об успехе.

Оба варианта дешевле, чем родитель узнаёт об этом только по факту провала клона.

### 6.4. `tag(quote, fruit)`

```
tag(
  quote: string,  # дословная цитата, тем же протоколом ретрая, что и у prune (см. §3)
  fruit: { ... }  # summary (обязательное), files_touched, gotchas
)
```

Закладка без среза: адресация границы и запись в дисковый архив (`recordDistillate`, см. §6.1) происходят так же, как у `prune`, но никакое правило переписывания демону не отправляется — отмеченный диапазон остаётся живым в контексте как ни в чём не бывало. Смысл — пометить участок как ценный для понимания «на будущее» (для следующих поколений агентов в этом же проекте, не только для текущей сессии), и чтобы его можно было найти и вытащить через `graft` позже, независимо от того, доживёт ли он в живом контексте до конца сессии или будет позже срезан обычным `prune`.

### 6.5. `graft(target?)`

```
graft(
  target?: string  # rule_id записи из оглавления capsule.md любой сессии этого проекта
)
```

Частичная реализация того, что §10 изначально намечал как режим «interrogate» — но проще: без живого форка или пересборки контекста, чистое чтение с диска.

- Без `target` — возвращает оглавление (`capsule.md`) **только текущей сессии**: список записей `prune`/`tag` с их `rule_id`, дёшево независимо от возраста проекта.
- С `target = rule_id` — ищет запись в общем по проекту индексе (`.mekiri/capsule-index.jsonl`), который покрывает **любую сессию, когда-либо запускавшуюся в этом проекте**, не только текущую; находит сессию и диапазон строк, читает полное тело записи из `report.md` той сессии и возвращает его, обёрнутым метаданными восстановления (`event`, `session`, `timestamp`).
- Работает как чтение из плоского архива на диске, а не из живой сессии — переживает компактизацию и завершение сессии по конструкции, а не по счастливой случайности.

### 6.6. `nudge-hook`: принудительное напоминание через PostToolUse

Не MCP-тулза, а отдельный PostToolUse-хук (`bin/nudge-hook.ts`), который подключается напрямую в Claude Code settings и получает на stdin JSON с `session_id`/`tool_name`/`cwd` после каждого вызова любой тулзы. Существует потому, что мягкий совет-подсказка без последствий на практике не работает: агент читает эскалирующийся текст как рекомендательный, каждый раз решает «эпизод ещё не закрыт» и ни разу добровольно не зовёт Mekiri-тулзу за всю сессию, даже когда подсказка уже сработала.

Состояние (`NudgeState`) хранится по сессии в `.mekiri/hook-state/<session_id>.json`:

```
{ callsSinceReset, threshold, consecutiveIgnored }
```

- `threshold` — случайное целое из `[2, 10]`, статистическая замена «логический блок работы только что закрылся» (хук видит по одному вызову тулзы за раз, без кросс-вызовной семантики).
- Любой вызов тулзы `mcp__mekiri-proxy__*` (`isMekiriTool`) сбрасывает `callsSinceReset` и `consecutiveIgnored` в 0 и передёргивает `threshold` — это единственный способ доказать, что агент реально среагировал.
- Когда `callsSinceReset` достигает `threshold`, хук отдаёт мягкий `additionalContext` (текст напоминания, эскалирующийся по тону на 2-м и 3-м+ подряд срабатывании без сброса) через `hookSpecificOutput`.
- После `HARD_BLOCK_AFTER = 3` подряд проигнорированных напоминаний (без единого реального Mekiri-вызова между ними) хук вместо совета отдаёт `{ decision: "block", reason }` — самый сильный сигнал, который умеет PostToolUse (это обратная связь агенту, не отмена уже выполненного вызова тулзы), и продолжает блокировать каждый следующий не-Mekiri вызов, пока состояние не сбросится реальным вызовом Mekiri-тулзы.

### 6.7. `metrics(scope?)`

```
metrics(
  scope?: "session" | "project"  # по умолчанию "session"
)
```

Тонкая обёртка над `computeProjectReport` (см. §12.2) — без неё числа по эффективности отката/форка были видны только через одноразовый скрипт, читающий mekiri-core напрямую, что и обнаружилось при первом реальном запросе метрик в рамках дневного дизайн-сеанса.

- `scope: "session"` (по умолчанию) — дерево, чей `rootSessionId` совпадает с `sessionId` текущего вызова. Проводной (wire-level) `prune`, в отличие от форка `mekiri-host`, никогда не меняет реальный `sessionId` текущей сессии — поэтому `rootSessionId` собственного дерева всегда равен ему напрямую, без обхода узлов. Если для этой сессии ещё нет ни одной записи в `audit.jsonl` (ничего не откатывали и не форкали) — `{ status: "not_found" }`.
- `scope: "project"` — все деревья сессий проекта разом (`ProjectMetricsReport.trees`), для сравнения между сессиями или ретроспективы за более долгий период.
- Возвращает `TreeMetricsReport` (или массив таких отчётов для `project`): `pruneCount`, `sproutCount`, `averageDistillationRatio`, `averageBranchCompression`, `totalLifetimeTokenSavings`, `totalContextProduced`, `contextRecyclingRatio`, `virtualContextLifetime`. Подробности каждого поля и формулы — §12.2.

## 7. Скиллы: когда что применять

Модели калибруются по контрастным примерам границы лучше, чем по абзацам критериев.

### 7.1. Гейт выбора клон / чистый субагент / инлайн — три вопроса по порядку

**Вопрос 1:** задача вообще диспетчеризуема? Если по ходу решения потребуется вмешательство пользователя, коррекция курса, невозможность сформулировать задачу одним заходом — ни клон, ни чистый субагент не годятся, независимо от актив/балласт. Смысл форка — изоляция плюс единственный отчёт на выходе, это несовместимо с необходимостью держать руку на пульте. Такая работа — инлайн, в главном потоке.

**Вопрос 2 (если да):** унаследованный контекст сейчас — актив или балласт? Используй тёплый клон, если наследуемый контекст — актив, а нужен не процесс, а результат. Используй чистого агента, если наследуемый контекст — балласт или источник предубеждений.

**Вопрос 3 (для клона, по ходу работы):** контекст остаётся активом? Если внутри инстанса всплывают признаки застревания — см. §6.3, право на самоэскалацию.

**Вопрос 4 (для инлайн-работы, по завершении):** побочный эпизод закрыт? Ответ «нет» на вопрос 1 не значит, что грязь остаётся навсегда — это лишь значит, что клон/субагент не годились *в начале*. Если по ходу инлайн-работы стало ясно, что её кусок был на самом деле побочным эпизодом (починка бага внутри работы над фичей, а не сама фича), а не главной задачей, и этот эпизод завершён с результатом — его можно закрыть тем же `prune(portal)` постфактум, даже если реального выбора «клон или инлайн» в начале не было. Обычно это частая мелкая гигиена по ходу (см. [whitepaper.md §4.1](whitepaper.md#41-почему-дистилляция-при-откате-качественно-лучше-компактизации)); реже — один откат покрупнее в конце эпизода, ретроактивно захватывающий и более ранние мелкие (см. §3 про вложенные откаты), с тем же эффектом, что дал бы warm sprout, если бы его можно было предвидеть заранее.

| Ситуация | Инструмент |
|---|---|
| «Прочитал 1000 строк логов, причина найдена, логи больше не нужны» | `prune(portal)` |
| «Гипотеза про сериализацию не подтвердилась, три захода впустую» | `prune(death_reload)` |
| «Нет, ты всё понял не так, ты сломал X» — фидбек пользователя в живой сессии | `prune(death_reload, trigger: user_feedback)`, а не попытка залатать поверх испорченного понимания |
| «Разберись с этим багом, пока я продолжаю фичу» — нужно всё текущее понимание | `sprout` |
| «Сходи в доки, найди формат вызова этого API» — опыт родителя не нужен | чистый субагент |
| Клон часами уверен в неверной гипотезе | самоэскалация клона (§6.3) или изначально чистый субагент |
| «Почини, но я хочу видеть каждый шаг и решать, куда дальше» | ни то ни другое — инлайн |
| Чинил баг инлайн (нельзя было предвидеть заранее), баг починен, задача была явно не главной | `prune(portal)` постфактум — ретроактивная компрессия побочного эпизода (Вопрос 4) |

## 8. Пре-компактный снапшот

Компактизация — lossy-сжатие. Делаем его обратимым: обёртка перед компактом сохраняет полный транскрипт под отдельным id (копирование файла, бесплатно) и указывает этот id в пост-компактном уведомлении.

**Оговорка о точке снапшота:** «за миг до компакта» не годится. Такой снапшот — контекст на грани переполнения; при попытке рехидрировать его для допроса компактизация сработает автоматически ровно в момент запроса. Правильная точка — за ~2 хода до компакта, либо снапшот на грани плюс встроенный «антикомпакт-механизм», отключающий автокомпакт на время допроса.

**Сценарий:** через час после компакта выплывает, что суммаризация съела важный смысл. Агент поднимает снапшот через тот же `spawn` с вопросом — и версия себя до компакта отвечает с полным контекстом момента. Дорого (полный префикс, кеш давно истёк), но платится только когда потеря реально выплыла.

## 9. Токеномика

Оба сценария кеш-эффективны почти идеально, потому что оба предполагают мгновенное использование контекста:

- **Откат:** диалог только что использовался → префикс горячий. Платим только за новый хвост-дистиллят.
- **Клон:** создаётся «здесь и сейчас» → читает родительский префикс из кеша по кеш-цене.
- **Снапшот:** копирование файла, ноль токенов. Платим только при реальном допросе.

Метрики для валидации — формулы в §12; здесь фиксируем, что именно нужно сравнивать:

- Токены на решённую задачу (суммарный input с учётом кеш-скидки): prune vs baseline vs «только компактизация».
- Доля живого контекста к концу задачи: baseline после дебага — типично 20–30%, цель — 70+.
- Качество после грязной фазы + контрольная метрика честности механизма: частота повторных заходов в откаченные тупики (валидация дисциплины death_reload-заметок).

## 10. TODO: направления на будущее

Способность вызывать сессии с предсказуемым контекстом — половина технического решения. Вторая половина — гигиена использования архивных веток, листьев и пре-компактных срезов. Фаза 2+.

**10.1. Режим допроса (interrogate).** Третий режим у spawn, помимо work и обычного: read-only сессия — тулзы записи отрезаны, в инжектируемом сообщении явная рамка «ты архивная копия, тебя спрашивает твоё продолжение; ответь по своему контексту, ничего не делай». Без рамки проснувшийся агент с горячим намерением и устаревшей картиной мира попытается продолжить работу с точки заморозки и наломает дров в изменившемся проекте.

**10.2. Ветка как владелец домена (resume-with-delta).** Противоположный режим: спящая ветка будится не для допроса, а для работы — как ответственный за домен. Если ветка писала базу данных, логично, что она же делает будущие миграции. Но пробуждение обязано нести дельту: «прошло время, проект дорабатывался, вот что изменилось».

**10.3. Единая онтология.** Откаченный лист, завершённый клон, пре-компактный снапшот, доменный владелец — один тип объекта: файл сессии с id, рехидрируемый через spawn в одном из режимов (work / interrogate / resume-with-delta). Дерево сессий целиком становится исполняемым архивом.

**10.4. facts_pool — глобальный пул фактов** (roguelike мета-прогрессия / CDCL global clause base). Сейчас наследование строго по линии предок→потомок. В настоящем CDCL learned clauses кладутся в глобальную базу, доступную всему дереву поиска, а не только потомкам конфликтующей ветки. В roguelike-терминах — это перманентная валюта мета-прогрессии (как Тьма или Ключи в Hades/Dead Cells): каждый забег умирает целиком, но вносит вклад в общий пул, доступный всем будущим и никак не связанным с ним забегам. Предлагаемая реализация: death_reload/portal-заметки пишут факты с тегами домена в общий пул; новая ветка не получает его автоматически (это раздувало бы промпт каждой ветке), а может запросить по требованию через тулзу `query_facts(domain)`.

**10.5. Explicit merge (кроссовер).** Если клон A чинит баг, а клон B параллельно переписывает архитектуру того же модуля, их знания сейчас сходятся только когда оба вернулись в ствол, и ствол должен вручную сообразить, что они пересекаются. Настоящий кроссовер — операция, берущая дистилляты двух листьев и сливающая их в один инжект для третьей ветки (multi-parent spawn). У этого пункта, в отличие от остальных, нет чистой игровой метафоры — однопользовательские roguelike-жанры не знают операции «слить два прохождения в одно». Оставляем как чисто инженерный TODO без метафорического обоснования.

## 12. Встроенная система метрик

### 12.1. Методология

Цель системы метрик — не лабораторные бенчмарки и не сравнение моделей между собой, а показатели, вычисляемые автоматически по истории работы конкретного агента. Почему не A/B и что такое виртуальный baseline — см. [whitepaper.md §8](whitepaper.md#8-как-мы-измеряем-эффект-без-дорогих-ab). Здесь — конкретные формулы.

Все нужные данные уже содержатся в дереве сессий. Для каждого prune известны: длина удалённой ветки, длина записанного дистиллята, положение prune относительно истории, количество последующих запросов, факт и момент компактизации. Для каждого warm sprout известны: длина самостоятельной ветки, размер возвращённого отчёта, положение относительно основной ветки. Вся статистика вычисляется постфактум без дополнительного логирования и без вмешательства в работу агента.

### 12.2. Формулы

**Distillation Ratio** — насколько эффективно временный рабочий контекст был превращён в знания.

```
Distillation Ratio = длина удалённой ветки / длина fruit
```

Пример: удалено 12 400 токенов, fruit 510 токенов → Distillation Ratio = 24.3×. Чем выше значение, тем больше временных наблюдений удалось заменить компактным знанием.

**Branch Compression** — аналогичная метрика для warm sprout.

```
Branch Compression = длина ветки клона / длина harvest
```

Показывает, какой объём самостоятельной работы был возвращён в основной контекст в виде компактного результата.

**Lifetime Token Savings** — главная экономическая метрика системы. После завершения сессии дерево позволяет точно определить, сколько последующих запросов было сделано после каждого prune. Если было удалено R токенов, а после этого произошло N запросов, то предотвращённая повторная передача составляет:

```
R × N
```

Суммирование по всем prune даёт общую экономию токенов за сессию. Это не прогноз и не оценка, а точная величина, вычисляемая по истории дерева.

**Virtual Context Lifetime** — насколько prune и warm sprout продлили жизнь рабочего контекста. Строится виртуальная линейная сессия (все prune-ветки возвращаются в основной поток, все warm sprout считаются выполненными главным агентом), затем вычисляется момент, когда такой виртуальный контекст достиг бы лимита компактизации.

Пример: фактическая компактизация — 61-й ход; виртуальная — 34-й ход; продление жизни контекста — 79%.

**Context Recycling Ratio** — какая часть всего созданного за сессию контекста оказалась временным рабочим материалом и была успешно переработана в компактные знания.

```
Context Recycling Ratio = Σ удалённых prune-веток / Σ всего произведённого контекста
```

Высокое значение означает, что значительная часть контекста представляла собой промежуточные наблюдения, выполнившие свою задачу и не требующие дальнейшего присутствия в рабочей памяти.

## 13. План реализации

**Фаза 1 — ядро на Claude Code:**

- Бенчмарк на тестовой задаче с намеренно грязным дебагом; три метрики из §9/§12.
