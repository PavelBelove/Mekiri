# Прокси-подрезка на уровне провода: находка 2026-07-29

Записка фиксирует одно рабочее заседание: неверное исходное предположение о том, кто в проекте является "стволом" Mekiri, тупиковые пути, которые из-за этого предположения перебирались, и найденное рабочее решение — вместе с его первой эмпирической проверкой на реальном API.

## 1. Ключевое недопонимание (исправлено этим документом)

До этой сессии в проекте (см. `[[project-mekiri-status]]`, `[[feedback-rollback-hygiene-economics]]`) действовало неявное допущение: "стволом" Mekiri является сессия, запущенная через `mekiri-host` (`packages/mekiri-host`) — отдельный REPL, который сам владеет своим циклом `query()` Agent SDK и поэтому технически способен на настоящий `prune`/`sprout`. Управляющий агент (сессия Claude Code/VSCode, разговаривающая непосредственно с пользователем — то есть именно эта сессия) при этом считался "оркестратором снаружи", у которого просто нет своего `prune`-инструмента, и это принималось как структурное ограничение, а не как проблема для решения.

**Это было неверной постановкой задачи.** Реальный, самый ценный "ствол" Mekiri — не отдельный тестовый REPL, а именно **основная пользовательская сессия** (Claude Code в терминале/IDE-плагине), потому что она:
- самая долгоживущая среди всех агентных инстансов в проекте;
- получает больше всего прямого фидбека от пользователя (правки, коррекции, "нет, ты не так понял");
- накапливает больше всего контекста о проекте в целом.

Именно она в первую очередь должна уметь резать сама себя ("подрезка"), и только во вторую — заводить тёплых клонов (параллелизм — вторичная выгода, ради скорости; если время не считать, весь выигрыш по токеномике даёт именно подрезка: больше полезных шагов до принудительной компактизации, дольше живёт сессия при том же контекстном окне).

## 2. Почему "изнутри" это не чинится

Реальный `prune` — это не рядовой тул-вызов, а операция уровня хост-процесса: (а) форкнуть текущую сессию по цитате, (б) заставить **тот же** цикл `query()` на следующем шаге читать историю из нового `session_id`. `mekiri-host`/`repl.ts` умеет (б), потому что сам владеет своим циклом (механизм `pendingSwitch`). Claude Code CLI/VSCode-плагин, обслуживающий именно эту, основную сессию — тоже обёртка над тем же Agent SDK, с той же файловой структурой сессий, но агенту (мне) внутри него такой рычаг не выставлен.

Проверенные и отвергнутые пути:
- **Хуки/команды Claude Code** — нет tool-triggered примитива для переключения активной сессии; ближайший релевантный запрос в апстриме, GitHub issue [anthropics/claude-code#16976](https://github.com/anthropics/claude-code/issues/16976) (программный доступ к checkpoint/rewind в headless-режиме), закрыт статусом **"not planned"**.
- **UI-автоматизация клика** ("Fork conversation from here" в VSCode-плагине, реальная кнопка, найден внутренний протокол `forkConversation(sessionId, promptText, resumeAtMessageId)` → `{type:"fork_conversation", forkedFromSession, resumeSessionAt}` в `webview/index.js` расширения `anthropic.claude-code`) — технически кнопка есть и структурно похожа на то, что нужно `prune`, но триггер (иконка) появляется **только по наведению мыши**, не в Tab-порядке — надёжной хоткей-автоматизации не нашлось.
- **CDP/DevTools-инъекция в webview** — сработала бы точнее, но требует перезапуска VSCode с `--remote-debugging-port`, что убивает все текущие разговоры, включая тестируемый — цена непропорциональна ценности для итеративной проверки.

## 3. Найденное решение: прозрачный прокси на уровне HTTP

Ключевой сдвиг перспективы: пользователю (и в общем-то мне самому) не важно, *видна* ли подрезка в интерфейсе — важно, что реально уходит в API Anthropic и оплачивается/обрабатывается моделью. Значит точка вмешательства — не UI и не механизм сессий Claude Code, а **сетевой запрос** между клиентом (`claude` CLI/VSCode-плагин) и `api.anthropic.com`.

Claude Code читает переменную окружения `ANTHROPIC_BASE_URL` **один раз при старте процесса** и после этого шлёт вообще все запросы (включая внутренние агентные под-вызовы) на указанный адрес вместо `api.anthropic.com`. Это официально документированная переменная (для корпоративных шлюзов/биллинга), и по ней уже существует референсная реализация похожей идеи — LiteLLM Proxy умеет подменять `tool_result.content` на `[Cleared by context management]` или схлопывать всю историю в один системный префикс + последний вопрос, именно для трафика Claude Code.

**Архитектура:**
1. Локальный HTTP(S)-прокси, слушает `127.0.0.1:PORT`.
2. Claude Code настроен на него через `ANTHROPIC_BASE_URL=http://127.0.0.1:PORT`.
3. Прокси форвардит каждый запрос на настоящий `api.anthropic.com`, сохраняя заголовки (включая реальный `authorization`/OAuth-токен подписки) как есть.
4. Перед форвардингом прокси может переписать `messages[]` в теле запроса — **строго срез хвоста**: убрать "руду" (сырые ходы разведки с начала сессии или с прошлой точки среза) и заменить её на "бриллиант" (короткий дистиллят), сохранив всё, что произошло с момента среза до текущей живой кромки, и продолжая жить вперёд от дистиллята. Каждая следующая подрезка сворачивает в том числе и дистилят предыдущей — ретроактивное поглощение мелких заметок, как и описано в whitepaper.md §4.1.
5. Локальный `.jsonl`-транскрипт сессии и то, что видит пользователь в интерфейсе, при этом **не трогаются вообще** — на экране разговор выглядит как обычно; подрезается только то, что реально уходит по проводу.
6. `sprout` технически почти то же самое (снапшот текущих `messages[]` уходит отдельным вызовом на изолированную подзадачу, назад складывается только harvest) — вторичная задача, реализуется тем же прокси-слоем, если/когда понадобится параллелизм.

### Важная оговорка про Terms of Service

Этот механизм заворачивает трафик подписочной (OAuth, Pro/Max) аутентификации через собственный локальный прокси. Проверка (2026 год) показала: Anthropic в январе-марте 2026 внедрила серверную блокировку сторонних инструментов, использующих OAuth-токены Free/Pro/Max-подписки, включая детекцию "не тот харнесс шлёт запросы" — это ровно тот класс паттерна, который правилами трактуется как нарушение, независимо от мотива (мы не пытаемся использовать токен для стороннего инструмента, только переписываем контент собственного трафика Claude Code, но эксперимент это не отличает от запрещённого паттерна на уровне детекции).

**Решение владельца проекта (2026-07-29, явное, информированное)**: эксперимент проводить на реальном подписочном аккаунте, риск принят сознательно — при бане пострадает только этот аккаунт, не более широкая инфраструктура; есть план восстановления (новый аккаунт). Важно, что для конечных пользователей Mekiri решение в перспективе обязано работать именно через подписку (не только через отдельный API-ключ) — иначе основной сценарий использования не покрыт.

## 5. Референсная реализация прокси (рабочий прототип)

Черновой код лежал в session-scratchpad (эфемерно, не переживёт сессию) — рабочее ядро фиксирую здесь текстом, чтобы не потерять.

```js
// rewrite.js — минимальный прокси: ANTHROPIC_BASE_URL -> сюда -> настоящий api.anthropic.com
const http = require("http");
const https = require("https");
const fs = require("fs");
const zlib = require("zlib");

const PORT = 8791;
const UPSTREAM_HOST = "api.anthropic.com";
const RULE_FILE = __dirname + "/rule.json"; // {"active":true,"keepMessagesFrom":N,"distillateUser":"...","distillateAssistant":"..."}

function loadRule() {
  try { return JSON.parse(fs.readFileSync(RULE_FILE, "utf8")); } catch { return { active: false }; }
}

const server = http.createServer((req, res) => {
  const chunks = [];
  req.on("data", (c) => chunks.push(c));
  req.on("end", () => {
    let bodyBuf = Buffer.concat(chunks);
    const headers = { ...req.headers, host: UPSTREAM_HOST };

    if (req.url.startsWith("/v1/messages") && !req.url.includes("count_tokens")) {
      const parsed = JSON.parse(bodyBuf.toString("utf8"));
      const rule = loadRule();
      if (rule.active) {
        // Строго срез хвоста: keepMessagesFrom считается в "естественном" индексном
        // пространстве клиента (он всегда пересчитывает историю с нуля, не зная о
        // наших переписываниях), поэтому индекс просто растёт на 2 с каждым ходом
        // независимо от того, сколько подрезок уже случилось.
        const kept = parsed.messages.slice(rule.keepMessagesFrom);
        parsed.messages = [
          { role: "user", content: rule.distillateUser },
          { role: "assistant", content: rule.distillateAssistant },
          ...kept,
        ];
        bodyBuf = Buffer.from(JSON.stringify(parsed), "utf8");
      }
    }
    headers["content-length"] = Buffer.byteLength(bodyBuf);

    const proxyReq = https.request(
      { hostname: UPSTREAM_HOST, port: 443, path: req.url, method: req.method, headers },
      (proxyRes) => {
        res.writeHead(proxyRes.statusCode, proxyRes.headers);
        proxyRes.pipe(res); // прозрачный форвардинг ответа (включая SSE-стрим), без изменений
      }
    );
    proxyReq.on("error", (err) => {
      if (!res.headersSent) res.writeHead(502);
      res.end(JSON.stringify({ error: "proxy upstream error", message: err.message }));
    });
    proxyReq.end(bodyBuf);
  });
});

server.listen(PORT, "127.0.0.1");
```

Запуск: `ANTHROPIC_BASE_URL=http://127.0.0.1:8791 claude ...` (любой реальный `claude`-процесс — CLI или тот, что расширение VSCode запускает как `resources/native-binary/claude`).

## 6. Открытые вопросы / следующие шаги

1. Разобраться в точной механике `cache_control`-точек Claude Code (см. п.4) — нужно посмотреть тело реального запроса, не только `usage` в ответе.
2. Перенести логику среза из ручных JSON-правил в настоящий вызов `mekiri-core`'s `findBoundary`/дистилляции — сейчас в прототипе дистилят пишется руками в `rule.json`.
3. Продумать, как основная (эта) сессия сама решает **когда** резать и **что** писать в дистилят — то есть привязать mekiri-gate/mekiri-tuning к прокси-слою, а не только к `mekiri-host`.
4. Решить, как THIS-сессия сигнализирует прокси "режь сейчас, вот дистилят" — тонкий локальный control-channel (файл/сокет), не требующий сессии-хоста вообще.
5. `sprout` через тот же прокси — вторичный приоритет (параллелизм/скорость, не токеномика).

## 7. Найденное ограничение: провод-прокси НЕ увеличивает пробег до авто-компактизации (2026-08-04)

Проверка живого трафика этой самой сессии (реальные `prune`-вызовы через `mekiri-proxy`, метрики из `usage` в JSONL-транскрипте — см. `.mekiri/audit.jsonl` записи `064042fd.../removed=85159` и `b75eb301.../removed=38403`) подтвердила, что кеш переживает срез и частично сокращается (112458→95682, 102842→95682 токенов cache_read) — то есть п.4 экономики (стоимость хода, качество контекста модели) работает и на реальном, не синтетическом трафике.

**Но владелец проекта указал на нестыковку в самой постановке п.4/п.16 project-status-памяти**: формулировка "prune покупает реальную токеномику и более долгий полезный пробег сессии до принудительной компактизации" смешивает два разных эффекта, и второй, скорее всего, не работает для *этой* (proxy-based) реализации.

Причина — п.5 архитектуры этого же документа сформулирован явно: "Локальный `.jsonl`-транскрипт сессии и то, что видит пользователь в интерфейсе, при этом **не трогаются вообще**". Авто-компактизация Claude Code CLI/VSCode — решение, принимаемое **самим клиентом** до/независимо от текущего сетевого запроса (нужно ведь показывать индикатор заполненности контекста даже когда запрос ещё не отправлен). По непрямым, но небезосновательным данным (реальные строки `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE`, `CLAUDE_CODE_AUTO_COMPACT_WINDOW`, `CLAUDE_CODE_COLD_COMPACT`, `DISABLE_AUTO_COMPACT` найдены прямо в бинарнике `claude` через `strings`; официальная документация Anthropic не публикует точный механизм) триггер компактизации считается по **локальной эвристике над непорезанной локальной историей**, а не по `usage`-полю последнего реального ответа API. Раз локальная история прокси не трогает — а именно так и было спроектировано, — свежая компактизация будет наступать **в тот же самый ход**, что и без прокси. Прямого эмпирического подтверждения в этой сессии пока нет (авто-компактизация здесь ещё ни разу не сработала за время эксперимента), вывод основан на связке дизайн-решения п.5 + непрямых данных о механизме клиента — не на 100%-но задокументированном факте.

**Важное уточнение по объёму**: это ограничение специфично именно для proxy-подхода к *этой* (основной, Claude Code CLI/VSCode) сессии. `mekiri-host`'s собственный REPL, который реально владеет своим циклом `query()` и делает настоящий `forkSession` (п.1-2 этого документа, и весь п.15-17 project-status-памяти про DR/BC/VCL-метрики), **не имеет этого ограничения** — там локальная история и есть то, что реально форкается, так что пробег там продлевается по-настоящему. Ограничение касается только "внешнего", непрозрачного для агента клиента.

**Что из заявленной пользы остаётся в силе для proxy-подхода**: реальное снижение стоимости хода (доказано числами выше) и, вероятно, качество ответов модели (меньше отвлекающего мусора в контексте, который модель реально видит и должна игнорировать) — оба независимо ценны сами по себе. Не остаётся в силе: "дольше живёт сессия при том же контекстном окне" конкретно для этого клиента — над этим пунктом нужна отдельная работа (либо смириться с ограничением и явно переформулировать ценностное предложение прокси-варианта, либо искать способ дать клиенту сигнал о реальном сокращении, либо использовать `CLAUDE_CODE_AUTO_COMPACT_WINDOW`/`CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` как грубый независимый рычаг, что не то же самое, что использовать реальную экономию).

### 7.1. Прямая эмпирика ПРОТИВОРЕЧИТ выводу выше (обновление того же дня, 2026-08-04, позже)

Два независимых research-агента (`claude-code-guide`), запрошенные независимо, оба сошлись на выводе "триггер компакта — независимая локальная эвристика поверх нетронутого локального файла", но оба явно пометили это как **неподтверждённый вывод** (Claude Code closed-source, никто не видел реальный код триггера; опирались на строки в бинарнике и GitHub issues про баги `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE`).

Прямая проверка на реальном `compact_boundary`-событии этой самой сессии даёт другую картину. Строка события содержит поле `compactMetadata` с `preTokens` — реальное число токенов, которое Claude Code сам посчитал перед компактом:

- `compactMetadata.preTokens = 170185` (реальная запись из `.jsonl` этой сессии, событие в 13:50:27)
- Последний реально известный API `usage`-тотал (input+cache_creation+cache_read) непосредственно перед этим — **164461** (ход в 13:45:26, за 5 минут до компакта)
- Если бы `preTokens` считался по **полной нетронутой локальной истории** (включая то, что 2 реальных `prune`-среза этой сессии уже вырезали из провода — 123562 символа, это ~23000-24300 токенов по ранее измеренному коэффициенту 5.08-5.36 симв/токен), ожидаемое значение было бы **≈187500-188800**
- Реальное `preTokens=170185` отклоняется от "как будто провод не резался" гипотезы на ~17300-18600 токенов (~10-11%), а от реального (порезанного) usage — всего на 5724 токена (~3.5%)

Это прямая, количественная улика **из одного, но реального** события: `preTokens`, судя по всему, следует за тем, что реально ушло/пришло по проводу (то есть за тем, что видит и на что реагирует API), а не пересчитывается заново по полному нетронутому локальному тексту. Если это верно, то `prune` **действительно должен продлевать пробег** до авто-компакта, а не только снижать стоимость — то есть исходная цель прокси-подхода (см. диалог с владельцем проекта) вероятно достигается, вопреки выводу в §7 выше.

**Статус**: n=1 реальное измерение, оба research-агента дают противоположный (но явно неподтверждённый, inference-only) ответ. Нужна вторая независимая проверка — следующий `compact_boundary` в этой или другой сессии, с явным сравнением `preTokens` до/после активных `prune`-правил — прежде чем менять архитектурные выводы окончательно. До этого: §7 выше считать **устаревшим/неподтверждённым**, а не финальным ответом.
